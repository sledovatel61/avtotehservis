## 3. Блокер

### B1. Сохранение настроек с пустым списком рейтингов роняет `/` и `/about` в 500

**Файлы:** `site/src/pages/index.astro:256`, `site/src/pages/about.astro:136`; источник пустого списка — `site/src/pages/admin/settings/index.astro:35-38`.

В ветке «отзывов ещё нет» обе страницы безусловно разыменовывают первый элемент списка рейтингов:

```astro
/* index.astro:256 (и about.astro:136) */
<span><b>Яндекс.Карты</b> … <a href={S.ratings[0].url} …>Открыть карточку организации</a></span>
```

`ratings` может стать пустым **штатным действием владельца**: в `/admin/settings` три поля «Источник» — если их очистить (владелец не подтвердил цифры — а задание требует скрывать рейтинги до подтверждения), обработчик сохраняет `ratings: []`:

```ts
/* admin/settings/index.astro:35-38 */
setSetting('ratings', [0,1,2].map(i => ({...})).filter(r => r.source));   // → []
```

Воспроизведение (свежая БД, `migrate`+`seed`, 0 отзывов):

```
$ node -e "…insert or replace into settings(key,value) values('ratings','[]')…"
$ curl -s -o /dev/null -w '%{http_code}\n' localhost:4334/        # 500
$ curl -s -o /dev/null -w '%{http_code}\n' localhost:4334/about   # 500
17:59:02 [ERROR] TypeError: Cannot read properties of undefined (reading 'url')
    at Object.default (…/index_DOCqNoNH.mjs:69:1187)
    at Object.default (…/about_SwGRA0xa.mjs:48:1167)
```

То же через UI: `/admin/settings` → очистить три «Источник» → «Сохранить» → `302 …?msg=Настройки сохранены`, после чего `/` и `/about` — 500 (проверено, скрин-эквивалент — вывод выше); `ratings_visible` при этом `false`, то есть блок рейтингов на странице не выводится, но падение всё равно происходит.

Дополнительно: после очистки в форме не остаётся ни одной строки рейтинга (они рендерятся из `S.ratings.map`), поэтому **вернуть рейтинги через админку нельзя** — только правкой БД.

**Почему блокер:** главная страница и `/about` перестают открываться после обычного действия в админке; дефект не виден ни в тестах (`npm test` 48/48 его не ловит), ни в `health`.

**Предложение:**
1. `href={S.ratings[0]?.url ?? S.map_link}` (или ссылка на поиск Яндекс.Карт из настроек), в `about.astro` — то же; лучше вынести общий компонент «пустое состояние отзывов».
2. Разрешить добавлять/удалять строки рейтингов в админке (или хранить их как `ratings` без фильтра пустых, чтобы строка восстанавливалась).
3. Интеграционный тест: `settings.ratings = []` → `GET /` и `GET /about` = 200.

## 4. Major

### M1. Медиа, ставшее обложкой опубликованного кейса, удаляется из библиотеки

**Файлы:** `site/src/pages/admin/media/index.astro:17-31` (проверка `canDelete` только по `media.attached_to`), `site/src/pages/admin/cases/[id].astro:70-73` (действие «обложка» пишет только `cases.cover_media_id`, `attached_to` не трогает), удаление — `admin/media/index.astro:39-56`.

Сценарий (весь — через UI, без SQL):

1. Загрузить фото в библиотеку `/admin/media` (или публичным `/api/uploads`) — `media.attached_to = NULL`.
2. В опубликованном кейсе нажать «Сделать обложкой»: `cases.cover_media_id = <это медиа>`, `media.attached_to` остаётся `NULL`.
3. В `/admin/media` удалить это медиа — удаление проходит.

```
# после шага 2
case7 { id: 7, status: 'published', cover_media_id: 'upl_7QD9wPfSmy38' }
attached_to: { id: 'upl_7QD9wPfSmy38', attached_to: null }

# шаг 3
POST /admin/media action=delete id=upl_7QD9wPfSmy38
302 -> http://localhost:4330/admin/media?msg=Медиа%20удалено

# результат
media rows: [ {id:'upl_ai2B3pt9r5FH', attached_to:'case:7'} ]
case7 cover: { status: 'published', cover_media_id: null }
ls /tmp/rr5media/upl_7QD9wPfSmy38 → No such file or directory
```

Публичная страница после этого молча отдаёт статичную заглушку `case-1.svg` вместо фотографии опубликованного кейса — то есть «защита медиа опубликованной сущности» (§10 задания) обходится штатным действием, и владелец не получает ни ошибки, ни предупреждения.

Что работает: если медиа загружено через страницу кейса (`attached_to='case:7'`), удаление корректно отклоняется:
`302 → /admin/media?err=Нельзя удалить: обложка/медиа опубликованного кейса`.

**Предложение:** в действии `cover` дополнительно писать `UPDATE media SET attached_to=? WHERE id=?` (и снимать прежнюю привязку у предыдущей обложки), либо в `canDelete` проверять `EXISTS(SELECT 1 FROM cases WHERE cover_media_id=? AND status='published')` и то же для `news`. Тест: «обложка published-кейса из библиотеки → удаление запрещено».

### M2. Квота заявок и антифлуд обходятся подменой cookie `ats_cid`

**Файл:** `site/src/pages/api/leads.ts:22-27`.

```ts
const rlKey = `leads:${ipPart}|${cid}`;                 // квота 5/час
const af    = checkLimit(`af:${ipPart}|${cid}`, …);      // антифлуд
```

`cid` — значение cookie, полностью подконтрольное клиенту. Требование M3 формулировалось как «ключ **дополнить** cookie-идентификатором в дополнение к IP», а реализовано «IP **или** cookie»: достаточно присылать новый `ats_cid` на каждый запрос.

```
# 8 заявок, 8 РАЗНЫХ cookie, 8 разных idempotency_key
[(201, False) × 8]            leads в БД: 17 → 25   (+8)
# 8 заявок, ОДНА cookie
[201×5, 429×3 (too_many)]     leads в БД: 25 → 30   (+5)
```

Аналогично снимается антифлуд: 32 мусорных запроса с разными `ats_cid` — `{400: 32}`, ни одного 429.

**Почему major:** бот с любым HTTP-клиентом создаёт неограниченное число заявок → заваливает Telegram и почту владельца (реальные уведомления тонут), это ровно тот сценарий, ради которого писался rate-limit; и это не «не проверено», а воспроизведено.

**Предложение:** два независимых уровня — «жёсткий» по IP (например, `RATE_LIMIT_LEADS_IP=30/час`, антифлуд 60/10 мин на IP) и «мягкий» по `IP+cid` (текущие 5/час), считать оба. Тест: «10 валидных заявок с 10 разными `ats_cid` → после N-й 429».

## 5. Minor / Nit

1. **`alt` реального фото всё ещё говорит «фото появится после съёмки».** `index.astro:222`, `about.astro:107` передают этот текст как `fallbackAlt`, а `content.ts:76` подставляет его, когда у реального медиа пустой `alt`. Проверено: у кейса с загруженным JPEG в разметке `alt="РРевью: правка диска R18 после ямы — фото «до/после» появится после съёмки"`. Minor-3 первого ревью закрыт наполовину — скринридер по-прежнему слышит «фото появится». Предложение: для реального медиа без `alt` использовать нейтральное `«<title> — фото»`, фразу про съёмку оставить только статичным заглушкам.
2. **`tel:` теряет «+» после сохранения настроек.** `admin/settings/index.astro:18` чистит `phone_main_tel` через `replace(/\D/g,'')`; дефолт — `+79289065700`, после любого сохранения — `79289065700`, и шапка рендерит `href="tel:79289065700"` (`Header.astro:26,50`). Проверено. Предложение: хранить нормализованный `+7…` (добавлять `+`, если 11 цифр).
3. **Range за пределами файла — 206 вместо 416.** `media/[...path].ts:25` зажимает `start` в `size-1`, поэтому `Range: bytes=99999-100000` даёт `206 content-range: bytes 2023-2023/2024` (1 байт). По RFC 9110 при `start >= size` нужен `416` + `Content-Range: bytes */2024`. Заодно: `bytes=-500` (суффикс) и multipart-range отдают 200 полным телом — допустимо, но не по спецификации.
4. **`/media/<id>/` (со слэшем) → 301** на `/media/<id>` → 404, вместо прямого 404 (следствие `trailingSlash`). Не дыра, но лишний редирект в логах.
5. **Фото-ответы без `Content-Length`/`ETag`/`Last-Modified`** (`/media/<id>/master.jpg` — 200 chunked). Для immutable-кеша работает, но `Content-Length` полезен nginx и клиентам. Видео-ветка `Content-Length` отдаёт.
6. **`/services` показывает только 6 кейсов** (`services.astro:12`, `listPublishedCases(6)`); при 7 опубликованных самый старый исчезает со страницы услуг, ссылки «все кейсы» нет. На `/` и `/about` 7-й кейс виден — M1 закрыт, это отдельный нюанс лимита.
7. **Отзыв нельзя датировать.** В форме `/admin/reviews` (`index.astro:54-62`) есть автор, оценка, текст, источник, ссылка — но нет даты, `published_at` остаётся `NULL`, и на `/` отзыв выводится без даты, хотя текст страницы обещает «с источником **и датой**». Предложение: поле даты (по умолчанию — сегодня) или убрать «и датой» из текста.
8. **Захардкоженный телефон в двух местах:** `pages/500.astro:26` и `pages/api/leads.ts:65` — не меняются настройками (в шапке/футере/контактах телефон берётся из настроек — проверено: смена в админке отражается на `/`, `/about`, `/services`, `/contacts`).
9. **`photos` не сверяются с существующими загрузками:** `validation.ts:53` проверяет только формат `upl_…`. Заявка с `photos:["upl_ai2B3pt9r5FH"]` (чужое фото) и с несуществующим `upl_ZZZZZZZZZZZZ` обе принимаются с 201; в админке получаются ссылки на чужой/несуществующий файл. Эксплуатационно малозначимо (id 72-битные), но лучше `EXISTS(SELECT 1 FROM media WHERE id=? AND attached_to IS NULL)`.
10. **Generic-тексты zod для отсутствующих объектов:** для `car`, `preferred`, `idempotency_key` клиент получает «Неверный формат значения» (`validation.ts:92`), а не «Укажите марку» — в UI это не всплывает (форма всегда шлёт объекты), но API-сообщение бесполезно.
11. **Бэкап кладёт в каталог копии пустые `site.sqlite3-wal` / `site.sqlite3-shm`.** Работает, но мусор в архиве бэкапа; restore их не использует.
12. **`engines.node: ">=22.18"` при задании «Node 24»** — оставлено осознанно и объяснено в `README.md:38` (разрешено пунктом minor-7 задания). Nit.
