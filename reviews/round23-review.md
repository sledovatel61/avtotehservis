## 4. Major

### 4.1. Гейт контраста по-прежнему берёт лучший случай: условие `darkText` инвертировано относительно своего комментария

`site/scripts/render-about.mjs:180-190` и `:214-219`:

```js
const worst = (zone, excl = [], textDark = false) => {
  let wm = textDark ? 1e9 : -1;   /* textDark=false (наш случай: светлый текст) → ищем МАКСИМУМ */
  ...
  wm = textDark ? Math.min(wm, v) : Math.max(wm, v);
...
const ctr = (zone) => {
  const L = relRGB(parseRGB(zone.col));
  const darkText = L > 0.25;                 /* тёмный текст на светлой подложке */
  const bg = worst(zone, [], darkText);
```

Здесь `L` — яркость **цвета текста**. У светлого ivory `L ≈ 0,87`, у латунного brass `≈ 0,45` — оба
больше 0,25, то есть флаг `darkText = true`, и `worst()` берёт **минимум** яркости подложки, то есть
самый тёмный пиксель под текстом. Для светлого текста это **лучший** случай: чем темнее подложка,
тем выше контраст. Комментарий над функцией утверждает обратное («Теперь берётся максимум яркости»),
и в `about-geom.json` это видно по подложкам: `h1.bg = 9`, `featH3.bg = 11`, `featP.bg = 11` — это
минимумы, а не максимумы.

Проверка: тот же кадр, тот же бокс текста, но берём самый светлый пиксель (метод, заявленный
комментарием) — гейт обязан был бы упасть:

| элемент | «самый светлый пиксель бокса» | гейт |
|---|---|---|
| h1 @1440 | **2,07** | 17,41 |
| h3 карточки №1/2/3/4 | 5,11 / **3,79** / **4,23** / **3,59** | 17,17 |
| p карточки №1/2/3/4 | 5,86 / **4,42** / 4,55 / **4,11** | 10,90 |

То есть даже «мягкая» интерпретация (максимум по боксу, без учёта самих глифов) даёт провал h3 на всех
четырёх карточках и p на двух. По худшему глифу (§3) провал ещё заметнее. В круге 22 я указывал на это
же место; ответом стала правка комментария и появление ветки `textDark`, но полярность осталась прежней —
поведение не изменилось ни на одном числе (ср. r22: h1 17,88, r23: 17,41 — разница только из-за кадра).

Что нужно: `darkText` определять как «текст тёмный» = `L < 0.25` (или инвертировать выбор min/max),
затем пересчитать `about-geom.json` и прогнать гейт заново — он упадёт на карточках, см. §4.2.

### 4.3. Апскейл в цепочке остался, а отчёт помечает «ноль апскейла ✔»

`site/scripts/build-images.mjs`, блок 10e:

```js
const headBgM   = frame(sharp(scHead).extract({left:376, width:624, height:768}).resize(780, 960,  …))   // 624 → 780 = 1,25×
const textBgM   = frame(sharp(scText).extract({left:550, width:527, height:768}).resize(700, 1020, …))   // 527 → 700 = 1,33×
const featsBgM  = frame(sharp(scFeats).extract({left:490, width:395, height:768}).resize(720, 1400, …))  // 395 → 720 = 1,82×
```

`extract` вырезает кроп, следующий `resize` его увеличивает — это и есть «интерполяция вверх», которую
§A2 запрещает («кроп — только `fit: 'cover'` от мастера, без интерполяции вверх»). Гейт I3 сравнивает
ширину ассета с шириной **мастера** (780 ≤ 1376 — проходит), а не с шириной кропа, поэтому слеп.

Сюда же размеры из таблицы §A2: мастера генератора вышли 1376×768 вместо 1536×1024, поэтому вместо
`ab-head` 1440×900 получилось 1376×688, вместо `ab-t` 1280×920 — 1068×768, вместо `ab-feats` 1440×810 —
1365×768. Отсюда же растяжение слоя: шапка 1,046×, «Преимущества» 1,055×, **текстовая 1,35×** на
1440/1280 (это печатается WARN'ом и в отчёте раскрыто), на 1024 — 1,47× мобильным файлом.

Итог: «ассет ≤ мастер» выполнено, «без интерполяции вверх на каждом шаге» — нет. Отчёт при этом
утверждает «Апскейла нет: ширина каждого ассета ≤ ширины мастера (проверяет гейт I3 + мутант) — ✔»,
а в §A2 раскрывает только вертикальную интерполяцию, тогда как по ширине кропов она тоже есть (1,25–1,82×).

Что нужно: либо генерировать мастер в 1536×1024 (или хотя бы 1440 по ширине), либо резать мобильные
кропы с уменьшением до фактического размера (например `ab-feats-m` 400×780 с тем же слотом), а в гейт
I3 добавить пары «ассет → кроп мастера» и проверять ширину кропа, а не мастера.

### 4.4. В лайтбоксе каждого кейса под новым фото — «Фото появится после съёмки в сервисе.»


Что нужно: либо вычищать хвост так же, как на главной, либо подменять `data-sub` на нейтральную подпись
вида «Иллюстрация: пример работы по теме кейса». И в гейт добавить проверку собранного HTML на

запретить `filter`/`image-rendering`/`transform: scale` на слоях `ab-*` и `.gal-card img` (антиобход уже
есть для `opacity`, `display`, `visibility`, `height`, `picture`).

### 5.2. Подпись кейса обрезана и склеена с плашкой

`«пример работы»` (106 px) шире, чем прежнее `«до / после»` (87 px), а `.gal-cap` — `nowrap` с
`text-overflow: ellipsis` и без зазора: на 1440 `capW 373`, требуется 389; заголовок и плашка стоят
впритык (`gap = 0`), обрезка съедает конец заголовка и саму плашку — на экране читается
«Боковой порез шины — ремонт, R16пример ра…» (`case-caption-clip.jpg`). То же на 390 (нужно 391).
Затронуты 2 карточки из 3 видимых на 1440. Лечится `display:flex; gap:10px` с `min-width:0` у заголовка
или сокращением плашки до «пример».

### 5.3. Лайтбокс растягивает обложку 1,43×

`data-img` переведён на `ab-case-N-640.webp` (640×480), а показывает он её в боксе 918×689 CSS —
увеличение 1,43× (на DPR 2 — 2,86× в физических пикселях). В круге 22 в лайтбокс уходил `lg`-кадр из
`coverInfo`; теперь крупный файл не отдаётся вовсе. §A2 требовал «avif 26 / webp 38 КБ» на 640×480, но
для просмотра «на весь экран» стоит отдавать 1080-й кадр (файлы `ab-media-1080` уже 1080 шириной —
подошёл бы `ab-case-N-1080`, если сгенерировать).

### 5.4. `.about-media` на 1024 по-прежнему берёт 480-й файл при боксе 638 px

`sizes="(max-width:1024px) 46vw"` даёт слот 471 → браузер выбирает `ab-media-480`, рендер 638 px —
1,35×. С круга 22 не изменилось (там я писал об этом же), `sizes` предписаны заданием, но при новых
файлах 1080×675 это чинится одной строкой (`(max-width:1024px) 62vw`).

### 5.5. Фон текстовой секции растянут 1,35×, деталь на 768 — 0,98 при пороге 0,8

`ab-t` 1068×768 в слот 1440×1038 — 1,35× по обеим осям, `ab-t-m` 700×1020 на 1024 — 1,47×. Гейт это
печатает WARN'ом (потолок для текста 1,5), в отчёте раскрыто. Но `textBg.detailX` на 768 = **0,98** —
это в 1,2 раза выше порога 0,8 и вдвое ниже, чем у шапки (2,54); фактически «самый мягкий слой» страницы.

### 5.6. Трети фонов на мобильных не различаются: 0,2–1,7 при норме 3

WARN'ы гейта: 768 `.abh-bg` 1,7, 768 `.ab-text-bg` **0,2**, 390 `.abh-bg` 0,5, 390 `.ab-text-bg` 0,6
(4 замера из 10). Причина понятна — портретный кроп горизонтального кадра, ровный свет. Это не блокер
(в отчёте раскрыто), но метрика B1 круга 22 на мобильных больше не работает и проверяется только
предупреждением.
