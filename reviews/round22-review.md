## 4. Major

### 4.1. Контраст считается «наоборот»: `worst()` берёт самый тёмный пиксель подложки

`site/scripts/render-about.mjs:135-137`:

```js
const worst = (zone, excl = []) => { let wm = 1e9;
  ... wm = Math.min(wm, LUM(...)); return wm; };
...
h1: +ratio(IVORY, relLum(...[worst(h1z.h1), worst(h1z.h1), worst(h1z.h1)])).toFixed(2),
```

Для светлого текста на фотографии худший случай — **максимальная** яркость подложки, а функция берёт
минимальную. В результате в `about-geom.json` попадает лучший контраст из возможных, и он ещё и одинаков
на всех пяти ширинах (h1 = 17,88 / 17,88 / 17,86 / 17,88 / 17,78), хотя кадр на каждой ширине обрезан
по-своему — метрика зависит от самого тёмного пикселя файла, а не от того, куда попал текст.

Фактический замер по худшему глифу (1440, виз-кадр минус кадр с `visibility:hidden`, порог Δ≥90, фон под
глифом; 24 622 пикселя глифов h1):

| элемент | min | p1 | p5 | p50 | < 4,5 | порог задания |
|---|---|---|---|---|---|---|
| h1 «…где счёта» | **2,27** | 6,56 | 9,23 | 14,13 | 0,2 % | ≥ 7 ✗ |
| `.page-head .lead` | 5,67 | 8,70 | 11,09 | 15,58 | 0 % | ≥ 4,5 ✓ |
| lead текстовой секции №1 | **2,42** | 5,75 | 8,49 | 12,28 | 0,3 % | ≥ 4,5 ✗ (точечно) |
| lead текстовой секции №2 | **2,57** | 4,12 | 6,89 | 12,46 | 1,2 % | ≥ 4,5 ✗ (точечно) |
| `figcaption` | **4,23** | 7,15 | 8,04 | 13,27 | 0,1 % | ≥ 4,5 ✗ |
| `.fact b` / `.fact span` | 12,89 / 12,68 | — | — | — | 0 % | ✓ |

На 390 то же: h1 4,15 (0 % глифов < 4,5 — светлый столб ушёл из кадра), lead шапки 3,89, lead текстовой
2,90 при 2,4 % глифов < 4,5, `figcaption` 2,23.

Причина видна глазами: в кадре шапки есть вертикальный светлый столб (дверной проём/пилон), и слова
«где счёта» идут прямо по нему — кроп `h1-hotspot-1440.jpg`, фон крупно `h1-band-bg.jpg`. Смысл заголовка
читается, но порог ≥ 7 не выполняется, и заявленное «по худшему пикселю» — не худший пиксель.
Скрим шапки к тому же слабее всего сверху: `linear-gradient(180deg, rgba(11,20,16,.18), rgba(11,20,16,.34))`
(`sections.css:345`), а h1 стоит именно в верхней половине.

Что нужно: считать по максимальной яркости (плюс отдельно — по худшему глифу, как здесь), и либо усилить
скрим в полосе заголовка, либо сдвинуть кроп так, чтобы светлый столб не приходился на h1 и lead.

### 4.2. h3 всех четырёх карточек 6,37 — недобор 7 равномерно по всем карточкам

Тот же замер по карточкам (1440, 1191 пиксель глифов первого h3, `min = p1 = p5 = 6,37`, p50 6,47;
на 390 — 6,39/6,47):

| элемент | min | p50 | порог | вывод |
|---|---|---|---|---|
| `.feat h3` | **6,37** | 6,47 | ≥ 7 | **не выполнен** |
| `.feat p` | 6,47 | 6,72 | ≥ 4,5 | выполнен |

Это не пятно, а ровная величина по всей строке: скрим карточки плоский —
`.feat-bg::after{background:rgba(11,20,16,.66)}` (`sections.css:356`), поэтому h3 недобирает на всех
четырёх карточках одинаково. Гейт этого не видит, потому что для `featH3` используется тот же
инвертированный `worst()` и печатает 16,8/15,68/16,8/16,99/16,89. Достаточно поднять скрим примерно
до 0,74–0,76 (или добавить локальную подложку под текст) — `p` при этом останется с большим запасом.
Побочный эффект честного замера: числа карточек в `about-geom.json` нужно пересчитать, иначе гейт
продолжит подтверждать неверное.

### 4.3. Фоны отрисованы с увеличением 2,32× (шапка) и 2,25× (текстовая) на 1440

| слой | файл | слот на 1440 | масштаб отрисовки (`object-fit:cover`) |
|---|---|---|---|
| `.abh-bg` | `ab-head-1600` — **620×795** | 1440×375 | **2,32×** (1280 — 2,06×, 1024 — 1,65×, 768 — 1,24×, 390 — 0,63×) |
| `.ab-text-bg` | `ab-t-1440` — 640×1280 | 1440×1038 | **2,25×** (2,00 / 1,60 / 1,20 / 1,03) |
| `.ab-feats-bg` | `ab-feats-1600` — 920×576 | 1440×529 | **1,57×** (1,39 / 1,11 / 1,02 / 0,85) |
| `.feat-bg` | `ab-f1…f4-480` — 480×360 | карточки | 0,59–0,74 ✓ |

Для сравнения, соседняя секция, которую принимали в круге 21: `svc-bg-1600` — 1500×844 на слот 1440×~920,
то есть 0,96×. Здесь же кадр-мастер `head-raw.jpg` — 1408×768 и `media-raw` 1408×768, то есть разрешение
для десктопа было, но его срезали до 620×795 в `build-images.mjs:769`, а потом растянули на 1440.
На экране это мягкая, «замыленная» шапка и текстовая подложка (`about-head-1440-reviewer.jpg`,
`text-section-1440.jpg`); на DPR 2 увеличение удваивается. Имя файла `ab-head-1600` при ширине 620
вводит в заблуждение и как раз мешало заметить это раньше.

Отдельно: цифры «деталь 1,96 / 1,37 / 1,37» этот перекос не ловят — деталь считается как средний
градиент соседних пикселей уже отрисованного (растянутого) кадра, а растянутый кадр гладкий по
построению, поэтому порог 0,8 проходится с запасом даже при 2,3× увеличении. Деталь имеет смысл
дополнять проверкой «пикселей кадра на CSS-пиксель слоя» (здесь 620/1440 = 0,43).

### 5.7. `colRatio` на 768 = 1,06 — метрика «доля колонки» считает не ту колонку

`render-about.mjs` делит ширину фото на ширину первого ребёнка `.about-grid`. На 768 фото 718 px,
«колонка» 677 px, отношение 1,06 — фото шире собственной «колонки», потому что на этой ширине медиа
идёт в полноширинной строке. Порог ≥ 70 % выполнен с запасом, но само число в 768 не значит то,
что написано в подписи; лучше брать `parentElement` картинки.

## 6. Заявления автора, которые не подтвердились

1. **«Контраст по худшему пикселю»** — в коде считается минимум яркости подложки, то есть лучший случай.
   h1 = 17,88 в `about-geom.json` против фактических 2,27 по худшему глифу; у карточек та же картина
   (16,8 против 6,37). Это и есть §4.1 и §4.2.
2. **«`ab-head-1600` — запас по ширине»** — файл 620×795, на 1440 растягивается в 2,32× (§4.3).
   Имя не отражает ни ширину, ни назначение.
3. **«Оговорка про `naturalWidth`»** — здесь, наоборот, автор прав, и я это перепроверил: при файле
   720 px `naturalWidth` = 526 (плотностно-скорректированная ширина), реальную пиксельную ширину по
   нему не узнать. Моё первоначальное подозрение (§5.2) держится не на `naturalWidth`, а на
   несовпадении `sizes` (471) с фактическим боксом (638).
