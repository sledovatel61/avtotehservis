### 1. В коммите нет миграций — сайт не поднимается, тесты не запускаются

**Где:** `site/migrations/001_init.sql` (отсутствует). Причина — корневой `.gitignore:27` (`*.sql`).

```

Что видит владелец/деплойщик после `npm ci && npm run migrate && npm run start`:

```
$ curl -s -o /dev/null -w '%{http_code}' localhost:4321/        → 500

**Что сделать:** вернуть файл миграции и закрыть ловушку, чтобы он не выпал снова:
```bash

```
Плюс шаг «файл миграции в индексе» в чек-лист релиза: `git ls-files site/migrations`.

## Major

### 1. `/admin/media` — 404, хотя ссылка стоит в меню админки
`src/layouts/Admin.astro` ведёт пункт «Медиа» на `/admin/media`; страницы нет (та же причина — `media/` в `.gitignore`). Задание §9 требует раздел «Медиа: библиотека, размеры, удаление неиспользуемого», в PR заявлено «медиа-библиотека (удаление только непривязанного, автоочистка сирот 24 ч)». Фактически есть только автоочистка в `outbox.ts:63`; удалить медиа вручную нельзя, сироты чистятся, но библиотеки нет.
```
$ curl -b cookies -o /dev/null -w '%{http_code}' localhost:4321/admin/media → 404
```

### 2. Опубликованный кейс не появляется на сайте
Галереи берут `listPublishedCases(6)` (`index.astro:12`, `about.astro:12`, `services.astro:12`), сортировка — `ORDER BY sort, published_at DESC` (`content.ts:17`), а новый кейс получает `sort = MAX(sort)+1` (`admin/cases/new.astro:40`). В сиде уже 6 опубликованных кейсов — значит **каждый новый кейс оказывается седьмым и не попадает ни на одну страницу**. Проверено:

```
$ # опубликован кейс id=7 «Правка литого диска R17 после ямы», status=published
$ for p in / /about /services; do curl -s localhost:4321$p | grep -c 'Правка литого диска R17'; done
0
0
0
```
Главный сценарий требования — «владелец публикует работу с телефона» — формально работает, но результат никто не увидит. Ожидалось: новые выше старых, либо «показать все».
**Что сделать:** `ORDER BY published_at DESC, sort` (или `sort DESC`) и/или лимит с запасом + страница «все работы».

### 3. На публичной `/appointment` остался текст из мокапа: «в мокапе нет сети»
`site/src/pages/appointment.astro:195`:
```
Отправка имитируется 700–1200 мс: в мокапе нет сети. В продакшне заявка уходит на сервер…
```
Требование §6.1 («убрать все пометки „демо“ с публичных страниц») и проверка №28 нарушены; вдобавок текст прямо противоречит поведению — заявка действительно уходит. Виден каждому клиенту на шаге 5.

### 4. Rate-limit съедает квоту на отклонённых заявках — 5 опечаток закрывают запись на час
Лимит проверяется **до** разбора и валидации тела (`src/pages/api/leads.ts:18`), а ключ — только IP. Проверено:
```
bad 1..5 → 400
валидная заявка → 429 {"code":"too_many"} , Retry-After: 3600
```
То есть клиент, который пять раз поправил телефон/год (или бот-сканер с того же IP, или соседи по CGNAT мобильного оператора), не сможет отправить заявку в течение часа. Это ровно тот класс проблем, ради которого ревью и делается: теряются заявки.
**Что сделать:** считать в лимите только успешные создания (`201`), а неуспешные — отдельным, более щедрым счётчиком; ключ дополнить чем-то кроме IP (например, cookie), либо повысить лимит и оставить отдельный антифлуд на 1 запрос/сек.

### 5. `systemd`-юнит ищет приложение не там, куда его кладёт `deploy.md`
`deploy/avtotehservis.service:11` — `WorkingDirectory=/var/www/avtotehservis/site`, `ExecStart=/usr/bin/node dist/server/entry.mjs`.
`deploy/deploy.md:32-33` — `git clone … repo && cd repo/site`. Итог: код лежит в `/var/www/avtotehservis/repo/site`, юнит смотрит в `/var/www/avtotehservis/site` → `Cannot find module dist/server/entry.mjs`, сервис в рестарт-лупе. Там же `scripts/backup.sh` по умолчанию берёт `SITE_DIR=/var/www/avtotehservis/site`. В остальном `deploy.md` ссылается на `repo/site` — рассогласование только в двух файлах. Локально воспроизвести systemd не мог, но путь в юните и путь из инструкции не совпадают буквально.

### 6. `http2 on;` в nginx.conf не понимает nginx целевых дистрибутивов
`deploy/nginx.conf:22`. Директива `http2` появилась в nginx **1.25.1**; Debian 12 (рекомендован в `deploy.md:3`) несёт nginx 1.22, Ubuntu 22.04 — 1.18, Ubuntu 24.04 — 1.24. На них `nginx -t` падает с `unknown directive "http2"`, то есть шаг «nginx -t && systemctl reload nginx» не проходит.
**Честно:** nginx в песочнице нет, `nginx -t` я не запускал — вывод по версиям дистрибутивов. Проверить на VPS одним `nginx -t`. Правится строкой `listen 443 ssl http2;` (работает и в старых, и в новых) либо требованием nginx ≥ 1.25.1 в инструкции.

## Minor / Nit

1. **Health-check не видит немигрированную БД.** `src/pages/api/health.ts` делает `SELECT 1`, поэтому на пустой базе отдаёт `{"status":"ok","db":true}` (200), пока `/` отдаёт 500. В `db.ts:37` уже есть `isMigrated()` — стоит использовать её и отдавать `503 degraded`.
2. **Английские тексты ошибок zod уходят клиенту.** `{"fields":{"car.year":"Too big: expected number to be <=2026"}}` — в форме это может показаться под полем. Нужны русские сообщения (`z.number().max(2026, 'Год — от 1980 до 2026')`).
3. **Нет `aria-current="page"` в шапке.** Активный пункт помечен только классом `is-active` (`Header.astro:17-22`), скринридер текущую страницу не объявит. Крошки `aria-current` имеют.
4. **Слоты 09:00–18:00, а не 09:00–19:00** (`slots.ts:4`, 10 слотов). Так же было в утверждённом мокапе, поэтому это не расхождение с дизайном, но проверка №7 задания («слоты 09:00–19:00») формально не выполнена. Решить и зафиксировать: либо 11 слотов, либо трактовать 18:00 как последнее начало работ.
5. **`alt` с «Заглушкой» прибит намертво.** `index.astro:131`, галерея кейсов: `alt="Заглушка: фото рабочего бокса появится после съёмки"`. После загрузки реального фото скринридер продолжит говорить «Заглушка…». Лучше брать `media.alt` и оставлять «заглушку» только для `/img/*.svg`.
6. **CSRF-отказ отдаёт голый текст `CSRF` (403)** в `admin/cases/new.astro:20`, `news/new.astro:18`, `settings/index.astro:14`. Пользователь видит белую страницу с одним словом. Лучше редирект с сообщением или оформленная 403.
7. **16 МБ файл полностью буферизуется в память до проверки** (`uploads.ts:20-22` → `media.ts:41`). При `client_max_body_size 110m` и `MemoryMax=700M` загрузка 100 МБ съест память до отказа. Стоит проверять `content-length` и резать поток.
8. **`RATE_LIMIT_LEADS` / `RATE_LIMIT_UPLOADS`** используются кодом, но отсутствуют в `.env.example` и `deploy.md` — оператор о них не узнает.
9. **`README.md` и описание PR расходятся с коммитом**: «`npm test` — 44/44», «выдача `/media/*` immutable + Range», «медиа-библиотека», «все 12 админ-маршрутов 200». На `b8cb474` это неверно (тесты 8/44, `/admin/media` 404, маршрута медиа нет). Для ревью это важно: отчёт «проверено» должен соответствовать тому, что реально в коммите.
10. **`restore.sh` привязывает архив медиа к `basename(MEDIA_DIR)`**: бэкап пакует `basename`, restore распаковывает в `dirname` — при смене имени каталога медиа уедет не туда. На боевой конфигурации (`/var/lib/avtotehservis/media` в обоих местах) не проявляется.
11. **Nit:** `/admin/logout` отвечает на GET редиректом, хотя выход — POST; безопасно, но лишний маршрут.

## Замечания к заданию (§6.3)

1. **`.gitignore` репозитория — мина под `site/`.** Корневой `*.sql` и `media/` молча выкидывают `migrations/001_init.sql` и `src/pages/media/**`. Стоит добавить в задание этапа 4 явное требование: «в репозитории обязаны быть `site/migrations/*.sql` и маршрут выдачи медиа; проверить `git ls-files`». Это уже второй агент, который мог наступить на это же.
2. **Критерий №7 «слоты 09:00–19:00»** допускает две трактовки (11 начал или 10 начал при работе до 19:00). В утверждённом мокапе — 10. Стоит зафиксировать в задании одну цифру, иначе ревьюер и автор меряют разное.
3. **Проверка №50 (Lighthouse)** невыполнима в песочнице без Chrome. Предложение: либо разрешить прикладывать `lighthouse-ci` в CI с публичным раннером, либо заранее договориться, что это «не проверено» и не влиять на вердикт.

## Итог

**До деплоя обязательно (blockers):**
1. Вернуть `site/migrations/001_init.sql` (и исключение в `.gitignore`), проверить `npm test` на чистом клоне.
2. Вернуть маршрут `/media/*` и исключение для `src/pages/media/` в `.gitignore`, проверить, что фото кейса открывается на публичной странице.

**До деплоя желательно (major):**
3. Вернуть `/admin/media` (или убрать пункт меню и честно записать «нет»).
4. Починить порядок кейсов — иначе публикация с телефона бессмысленна.
5. Убрать с `/appointment` текст «в мокапе нет сети».
6. Пересчитать rate-limit так, чтобы отказы не блокировали запись.
7. Привести `systemd`/`deploy.md`/`backup.sh` к одному пути.
8. Проверить `nginx -t` на целевом дистрибутиве и поправить `http2`.

**Можно после деплоя:** minor-список (health-check, русские сообщения zod, `aria-current`, alt, CSRF-страница, лимит размера загрузки, env-переменные, README).
