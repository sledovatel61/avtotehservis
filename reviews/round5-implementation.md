## 3. Блокер

### B1. Лимиты «по IP» и блокировка перебора пароля обходятся подделкой `X-Forwarded-For`

**Файлы:** `site/src/server/http.ts:18-22` (`clientIp`), `site/src/server/admin-auth.ts:18-21` (`loginRateKey`), `site/deploy/nginx.conf:67,76`; новые лимиты — `site/src/pages/api/leads.ts:22-33`.

```ts
/* src/server/http.ts:18 */
export function clientIp(ctx) {
  const xff = ctx.request.headers.get('x-forwarded-for');
  if (xff) return xff.split(',')[0].trim();   // ← ПЕРВОЕ значение присылает клиент
  return 'local';
}
```

```nginx
# deploy/nginx.conf:76
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # = "<что прислал клиент>, <реальный IP>"
```

`$proxy_add_x_forwarded_for` дописывает реальный адрес **в конец**, а приложение берёт **первый** элемент — то есть ровно то, что прислал клиент. От этого значения зависят: новый «жёсткий» лимит заявок (`leads-ip:*`), антифлуд (`af-ip:*`), лимит загрузок (`uploads:*`), ключ блокировки входа (`login:*`) и `ip_hash` в карточке заявки.

**Воспроизведение 1 — обход жёсткой квоты (30/час):**

```
# 30 заявок с X-Forwarded-For: 1.1.1.1  → 30 × 201, 0 × 429
# 31-я с тем же XFF                     → 429        ← лимит реально работает
# с другим XFF 2.2.2.2                  → 201
# с другим XFF 3.3.3.3                  → 201        ← бакет новый, лимита нет
```

31-я и последующие заявки создаются в БД и уходят в Telegram/на почту владельца — ровно тот сценарий, ради которого делался M2.

**Воспроизведение 2 — блокировка перебора пароля снята полностью:**

```
# 8 попыток входа с паролем wrong1…wrong8, XFF: 10.9.0.1…10.9.0.8
1..8: «Неверный логин или пароль»     ← блокировки нет ни на одной попытке

# контроль: 6 попыток без XFF (один IP)
1..5: «Неверный логин или пароль»
6:    «Слишком много попыток входа. Повторите через 15 минут.»   ← штатная защита
```

То есть 5 попыток / 15 минут (`LIMITS.login`) превращаются в неограниченный перебор пароля администратора: достаточно менять один заголовок. Ни один из 52 тестов этого не ловит — в `site/tests/**` нет ни одного упоминания `X-Forwarded-For` (`grep -rn "X-Forwarded-For" site/tests` → пусто).

**Почему блокер:** это дыра в защите (перебор пароля владельца) и обесценивание только что сделанного M2: в конфигурации из `deploy/` (единственная описанная в `deploy.md`) лимиты обходятся тривиально.

**Предложение (любое из двух, лучше оба):**
1. В `deploy/nginx.conf` перезаписывать заголовок, а не дописывать: `proxy_set_header X-Forwarded-For $remote_addr;` (один прокси — доверенный) и читать в приложении `X-Real-IP`/`X-Forwarded-For` как единственный адрес.
2. В `clientIp()` брать **последний** элемент `X-Forwarded-For` (ближайший к приложению доверенный хоп) либо вообще `X-Real-IP`, а если ни одного нет — считать адрес неизвестным и применять общий лимит, а не `'local'`.
3. Тест: 10 запросов с разными `X-Forwarded-For` при жёстком лимите 3 → `429` уже на четвёртом; `admin.test.ts` — 6 попыток входа с ротацией заголовка → блокировка на 6-й.

## 4. Minor / Nit

1. **Доп. телефоны — «мёртвая» настройка и мёртвый код.** `settings.phones_extra` заполнена (Приёмная +7 (863) 229-19-50, Ремонтная зона +7 (951) 826-58-47), в админке есть поля «Доп. 1/2 — название/показ/tel», но на сайте эти номера не выводятся: сохранил `+7 (863) 111-11-11` / `+7 (951) 222-22-22` → **0 вхождений** на `/`, `/about`, `/contacts`, `/services`, `/appointment`, `/news`, `/privacy`, `/404`. Причина — `const E0/E1 = S.phones_extra[..]` объявлены и ни разу не использованы **в 14 файлах** (`Header`, `Footer`, `Dock`, `Modals`, `index`, `about`, `contacts`, `appointment`, `news`, `news/[slug]`, `services`, `services/[slug]`, `privacy`, `404`). Отсутствие самих номеров согласуется с `docs/06-fact-check.md` («публиковать после подтверждения владельцем»), но тогда непонятны рабочие поля в админке и мёртвые переменные — это тот же класс, что «мёртвый код на /services», который в этом же коммите убран. Предложение: либо выводить номера (например, в блоке контактов при заполнении), либо убрать поля из админки и `E0/E1` из 14 файлов.
2. **`Range: bytes=100-50` → 500.** В `media/[...path].ts` проверяется только `start >= size`; при `end < start` `Buffer.alloc(end-start+1)` получает отрицательный размер → страница 500. Проверено: `curl -H 'Range: bytes=100-50' …/original.mp4` → `500`. Баг не новый (был и в `837b349`), но стоит рядом с исправленным 416: корректно вернуть `416` или `200`.
3. **`bytes=-500` (суффиксный диапазон) и `bytes=abc` → 200 полным телом.** Допустимо, но по RFC 9110 суффиксный диапазон — `206` с последними 500 байтами. Nit.
4. **Nit формулировки:** для скалярного поля сообщение «Ключ идемпотентности: заполните блок» звучит странно (метка задумывалась для объектов `car`/`preferred`). Проверено в ответе 400.
5. **Nit:** если `X-Forwarded-For` отсутствует, `clientIp()` возвращает `'local'` — все клиенты попадают в один бакет. В описанной схеме с nginx этого не происходит, но при прямом запуске `npm start` лимит 5/час станет общим на весь сайт. Связано с B1 и закроется тем же исправлением.
6. **Снятое замечание прошлого раунда:** minor «`/services` показывает только 6 кейсов, 7-й исчезает» был основан на вызове `listPublishedCases(6)` в коде, а не на выводе страницы — проверка показала, что карточек кейсов на `/services` не рендерилось вовсе. Мёртвый код удалён корректно, замечание снимаю (и фиксирую как мою ошибку второго раунда).
