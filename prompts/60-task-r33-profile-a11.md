## 2. Где именно плохо — по живому кадру

Кадры живого прод-режима (`BG3D=voyah-free BG3D_DEMO=1`), 1440×900 и 390×844:
`docs/reports/r33-bg-car/pub-1440.jpg`, `pub-390.jpg`. Сравнение с фото одного масштаба:
`docs/reports/r33-bg-car/ref-vs-ours.jpg` (сверху фото `docs/brand/voyah/refs/r31/side-white-1456.jpg`,
снизу наш кадр).

Что видно владельцу и мне:

1. **Кабины нет.** Верхняя кромка почти прямая и слегка падает к носу. У Voyah Free
   над передними сиденьями крыша поднимается аркой, а к корме падает — это и есть
   «стакан», по которому машина узнаётся. У нас этого перепада нет.
2. **Нос — вертикальная стенка.** Капот не поднимается от решётки, передок обрублен.
3. **Корма обрублена.** Пятой двери, наклона заднего стекла и спойлера не читается.
4. **Подоконная линия** (низ стёкол) гуляет и местами уходит ниже середины кузова,
   поэтому стекло выглядит как нашивка, а не как остекление между стойками.
5. **На 390 px машина спрятана за абзацем текста** — виден только белый обрубок у
   кнопки «Позвонить». Это тоже твоя зона (`Bg3dLayer`, кадр `B-silhouette-mobile-390x470`).

## 3. Главная проблема: мерим разными линейками

Три замера одного и того же силуэта дают три разных ответа, и ни одному нельзя верить:

| Источник | h/L | Чем мерил |
|---|---|---|
| паспорт машины | **0,335** | 1,645 м / 4,905 м — вот это верно |
| CPU-кадр `tools/bg3d/frames.mjs` (твоя же математика) | 0,265 | `npm run measure:bg-car` на `docs/reports/r33-bg-car/frames-cpu/B-silhouette-1280x720.png` |
| мой кроп браузерного скриншота | 0,447 | кроп 450×220, порог по яркости |
| маска `side-mask.png` | 0,337 | верхняя кромка по столбцам |
| моя первая версия `side-mask.png` (крупнейший компонент) | 0,235 | крыша в маску не попала |

Вдобавок сами измерители дают мусор: `bg3d-car-measure.mjs` на CPU-кадре нашёл
четыре «колеса» диаметром 13,9 / 9,8 / 9,5 / 18,1 %L — это бампер, тень и арки,
а не шины; паспорт колеса 15,03 %L (0,7375 м / 4,905 м).

**Каюсь по маске, это моя ошибка постановки:** `docs/brand/voyah/refs/r31/side-mask.png`
распадается на 138 связных компонентов, крупнейший имеет bbox h/L 0,235 (крыша потеряна),
а отражения витрины тянут хвост к носу. Порог IoU 0,97 против такой маски недостижим —
ты был прав, когда об этом написал. `profile-traced.json` тоже негоден как источник
формы: поле `bottom` там — линия земли, а не низ кузова.

**Поэтому первая часть задания — не форма, а инструмент.** Пока мерим разными линейками,
любая правка профиля будет угадыванием.

## 4. Что сделать

### Шаг 1. Один замер, которому можно верить

Сделай **одну** воспроизводимую процедуру сравнения нашего силуэта с фото и вставь её
в гейт (не отдельным скриптом «для отчёта»):

- эталон — **фото** `docs/brand/voyah/refs/r31/side-white-1456.jpg`, а не моя маска;
  контур снимается с фото заново (своя трасса, ручная правка спорных мест допустима
  и предпочтительна: крыша, порог, низ бампера);
- наш силуэт — CPU-кадр `node tools/bg3d/frames.mjs` (совпадает с шейдером по математике,
  без текста и без кропа), плюс живой браузерный кадр для контроля;
- нормировка: обе фигуры приводятся к длине 1000 px, **выравнивание по колёсам** (центры
  передней и задней оси) и по земле, а не по bbox — иначе ошибка уезжает в масштаб;
- печатать **таблицу ориентиров**: доля длины (0…100 %L) → верхняя кромка в %H, для
  фото и для нас, и разницу. Без таблицы отчёт не принимается.

Ориентиры, которые надо попасть (в долях длины от переднего бампера к заднему):

- передний бампер 0 %L, задний 100 %L;
- передняя ось **19,8 %L**, задняя **80,1 %L** (свесы 0,97 м + база 2,96 м + свес 0,97 м;
  в сцене это `CAR.axles = [-1.48, 1.48]` при длине 4,905 м);
- колесо Ø **15,0 %L** и одинаковое спереди и сзади (сейчас замер даёт разные — либо
  арка перекрывает шину, либо колёса разного размера в сцене: разберись);
- высота кузова **33,5 %L** — это твой главный числовой критерий, допуск ±1,0 %L;
- клиренс 0,18 м = 3,7 %L.

### Шаг 2. Профиль

Собери силуэт по ориентирам из шага 1, а не «на глаз»: капот с подъёмом от решётки,
лобовое стекло, крыша-арка над передними сиденьями, спад к корме, наклонная пятая
дверь, подоконная линия на постоянной высоте между стойками.

Проверяй себя таблицей из шага 1 после каждой правки. Цель: **все ориентиры в пределах
±2 %L**, h/L 0,335 ±0,010. Про «похоже/не похоже» в отчёте не пиши — только числа и кадры.

Если в текущем ракурсе (задняя три четверти) профиль в принципе не читается и требует
другого угла — можно предложить смену угла камеры, но **с доказательством**: кадры
«было/стало» и замер по той же таблице. Вёрстку страницы при этом не менять.

### Шаг 3. Гейты, которым сейчас нельзя верить

1. `npm run edge:shadow` (`scripts/bg3d-edge-shadow.mjs`) даёт **ложный PASS**: скрипт
   не читает `SHADOW_HALF` из `shader.ts`, а считает по своей формуле `0,97·L/2`;
   после твоих правок он мерит не то, что рисуется. Либо пусть читает константу из
   исходника (как `car-profile.ts` читается другими гейтами), либо удали гейт и напиши
   в отчёте, чем его заменить. Ложный PASS хуже отсутствия гейта.
2. `npm run car-profile` падает: нет `docs/reports/r31-car-profile/profile-ref.json`.
   Разберись, нужен ли этот путь вообще, или почини ссылку.
3. `npm run measure:side-iou` — если эталон пересобран по шагу 1, порог 0,97 имеет смысл
   только вместе с обоснованием: напечатай IoU фото-эталона против его же сглаженной
   оболочки и против независимой трассы, и поставь порог по этим числам. Если порог
   остаётся недостижимым — снижай и напиши, почему именно такое число.
4. `bg3d-car-measure.mjs` ищет «шины» пятнами и находит бампер — почини определение
   колёс (например, по центрам осей из `CAR.axles`, а не по пятнам), иначе он будет
   врать в каждом отчёте.

### Шаг 4. Мобильный кадр

На 390 px машина уходит под текст. Нужно, чтобы силуэт читался: сдвинуть/масштабировать
сцену в пределах текущего блока, не ломая сетку и safe-zone. Приложи кадр 390×844.
