**Кому:** Агент 6.
**Роль:** независимый ревьюер. Ты не пишешь код и не «помогаешь по-дружески» — ты ищешь то, что сломается у владельца в первый месяц.
**Что ревьюишь:** PR Агента 5 в ветку `arena/099a14c5-avtotehservis` — папка `site/`.
**Задание разработчика:** `prompts/04-implementation-task.md`.
**Утверждённый дизайн:** `mockups/round2b/agent-05/`.

## 0. Сообщение для отправки агенту

> Ты Агент 6, назначен независимым ревьюером этапа 4. Агент 5 внедряет свой мокап в `site/`. Твоя задача — проверить PR как чужой код: запустить, сломать, найти расхождения с требованиями и фактами. Задание — `https://github.com/sledovatel61/avtotehservis/blob/arena/099a14c5-avtotehservis/prompts/05-review-task.md`. Код не правишь, пушишь только свой отчёт в `reviews/`. Вердикт — по блокерам, с доказательствами.

---

## 1. Что считается хорошим ревью

1. **Проверено, а не прочитано.** Каждый вывод — с командой, выводом, кодом ответа, скриншотом или файлом:строка. «Выглядит нормально» — не вывод.
2. **Сначала запуск, потом чтение диффа.** Собери, подними, пройди сценарии — и только затем читай код.
3. **Ищешь не стиль, а риск.** Проблемы, из-за которых теряются заявки, ломается мобильная публикация, утекают персональные данные или сайт не проходит приёмку.
4. **Честность важнее полноты.** Не смог проверить — пиши «не проверял, причина», а не выдавай догадку за факт.
5. **Ни одного выдуманного бага.** Если сомневаешься — воспроизведи или помечай «предположение, не воспроизвёл».

## 2. Порядок работы

1. Забери PR: `gh pr checkout <номер>` (или ветку из PR). Зафиксируй коммит, который ревьюишь: `git rev-parse --short HEAD`.
2. Прочитай `prompts/04-implementation-task.md`, `docs/00-brief.md` (KPI/DoD), `docs/01`, `docs/07`, `docs/08`.
3. Собери с нуля: `cd site && npm ci && npm run typecheck && npm test && npm run build`.
4. Подними сервер на временной БД: `DATA_DIR=/tmp/review-data npm run migrate && npm run seed && npm run start`.
5. Пройди публичные сценарии через браузер/curl/jsdom.
6. Проверь админку: создай администратора, войди, опубликуй кейс, скрой, отредактируй.
7. Убедись, что `mockups/round2b/agent-05/` не изменён: утверждённый дизайн — эталон, а не рабочий материал.
8. Проверь доставку на заглушках: подними локальный SMTP-приёмник и заглушку Telegram (`TELEGRAM_API_BASE`), прогони успех/отказ/ретрай/ручную отправку.
9. Проверь безопасность и лимиты (список §3.3).
10. Проверь деплой-инструкцию: пройди по шагам, отметь, что выполнимо в среде, а что требует VPS.
11. Напиши отчёт и оставь ревью в PR.

**Чего в среде может не быть:** браузера, реального телефона, VPS, боевых SMTP/Telegram. Это не повод пропускать проверку — используй jsdom, curl, заглушки; а что физически не проверить, помечай `[не проверено]` и объясняй, что нужно.

## 4. Попробуй сломать

Это обязательная часть. Минимум по одному сценарию на пункт:

1. Двойная отправка формы и повторный POST с тем же ключом.
2. Обрыв сети после отправки (закрыть вкладку, вернуться) — черновик и номер не теряются.
3. Заявка в 23:59 на слот, который через минуту заняли.
4. VIN с `I`, `O`, `Q`, строчными, 16 и 18 символов.
5. Телефон `+7`, `8`, `+1`, с пробелами, с буквами.
6. Имя из 5000 символов, эмодзи, `<script>`.
7. Загрузка 100 МБ видео, 16 МБ фото, файла без расширения, `.svg` со скриптом.
8. Параллельные 10 заявок с одним ключом.
9. Telegram отвечает `403`/таймаутом; SMTP отвечает `550`; оба лежат.
10. Перезапуск сервера во время отправки outbox.
11. Истёкшая сессия и попытка сохранить кейс; CSRF-токен от другой сессии.
12. 20 неудачных входов подряд; вход с другого IP.
13. Прямой URL черновика кейса и скрытой новости.
14. Удаление медиа, привязанного к опубликованному кейсу.
15. Восстановление БД из бэкапа и проверка, что сайт поднялся.
16. Часы сервера в UTC: дата и слот не съезжают.
17. **Подделка заголовков клиента:** `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `X-Forwarded-Proto` — меняются ли от них лимиты, ключ блокировки входа, `ip_hash` в заявке, `Secure`-cookie. Проверять **и через прокси с конфигом из `deploy/`**, а не только прямыми запросами к приложению: приложение может быть право, а nginx — дописывать клиентский заголовок первым.

## 5. Северity и вердикт

| Уровень | Что это | Пример |
|---|---|---|
| **Blocker** | теряются заявки/данные, дыра в безопасности, нарушение 152-ФЗ, не работает основной сценарий, сайт не собирается | согласие не фиксируется; SQL-инъекция; форма падает |
| **Major** | требование не выполнено, KPI недостижим, мобайл/доступность сломаны, но обхода нет | нет ретраев; админка не работает на телефоне; Lighthouse 60 |
| **Minor** | работает, но плохо: ошибки в тексте, неудобство, нет состояния загрузки | нет фокуса после ошибки |
| **Nit** | стиль, нейминг, мелочи | лишний `console.log` |

**Вердикт:**

- есть хоть один **blocker** → `REQUEST CHANGES`;
- больше трёх **major** → `REQUEST CHANGES`;
- 1–3 major без блокеров → `APPROVE WITH COMMENTS` (исправить до деплоя);
- всё остальное → `APPROVE`.

Отдельно — статус гейтов:

- **G6** «загрузка фото/видео с телефона» — только реальное устройство владельца; если его не было, пиши `не проверено`, а не «пройден».
- **G7** «заявка проходит e-mail + Telegram + админку, Lighthouse ≥ 90» — только с боевыми доступами; иначе `не проверено` + список, что нужно.

### 6.2. Ревью в PR

- Общие выводы — комментарием к PR.
- Точечные — к строкам файлов, с предложением, а не только «плохо».
- Не аппрувь, пока блокеры не закрыты.

### 6.3. Правила поведения

- Код не правишь, в ветку автора не пушишь, `force-push` не делаешь.
- Можешь предложить патч в комментарии или отдельным diff-блоком.
- Не дублируй один и тот же вывод в пяти местах: одно замечание — один пункт.
- Не переходи на личности и не переписывай задание под себя.
- Если нашёл проблему вне `site/` (в задании, docs) — отдельным разделом «Замечания к заданию».

## 7. Повторное ревью

После правок автор присылает новый коммит. Ты:

1. Проверяешь **каждый** блокер и major из своего ревью — построчно, с командой на каждый пункт. «Исправлено» без вывода команды не считается.
2. Регресс: заново `npm ci` в чистом клоне, `typecheck`, `test`, `build`, плюс запуск по инструкции из `deploy.md`.
3. Отдельно проверяешь то, что в первый раз пропустил или считал неважным: гигиена PR (`git diff --name-status`), соответствие README фактам, health-check на немигрированной БД.
4. Дописываешь в тот же файл раздел `## Повторное ревью (дата, коммит)` с таблицей «было → стало → чем проверено».
5. Меняешь вердикт только по результатам проверки. Закрытый блокер без доказательства — не закрытый.

## 8. Критерий хорошего ревью

Владелец запускает сайт и в первый месяц не сталкивается с тем, что ты пропустил. Лучше десять подтверждённых мелочей и один честный «не проверял», чем «всё отлично» без доказательств.
