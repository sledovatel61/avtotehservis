## 3. Major — до деплоя

### M1. Новый кейс не виден на сайте

`content.ts:17` — `ORDER BY sort, published_at DESC`, лимит 6; в сиде 6 кейсов с `sort` 1…6; новый получает `sort = MAX+1 = 7` и не попадает никуда. Публикация с телефона формально работает, а результата не видно — это ломает главный сценарий требования.

**Сделать:** новые выше старых (`ORDER BY published_at DESC, sort DESC`), проверить, что седьмой кейс появляется на `/` и `/about`. Добавить в интеграционные тесты проверку «опубликовал → видно на публичной странице».

### M2. Убрать с публичной страницы текст мокапа

`appointment.astro:195`: «Отправка имитируется 700–1200 мс: в мокапе нет сети…». На боевой странице это ложь и прямое нарушение задания §6.1.

**Сделать:** заменить на честный текст про то, как работает отправка и когда клиент получит номер. Пройти все публичные страницы поиском `мокап`, `демо`, `заглушка`, `имитир` — остаться должны только пометки на изображениях-заглушках, и то переформулированные под владельца («фото появится после съёмки»), а не под разработчика.

### M3. Rate-limit не должен тратить квоту на отказы

Сейчас `checkLimit` считает **любой** запрос, включая отклонённые, а ключ — только IP. Пять опечаток в телефоне — и валидная заявка получает `429` на час.

**Сделать:**

1. Считать квоту **только на успешно созданные** заявки (`201` после `createBooking`/`createMessage`).
2. Для мусорных запросов — отдельный, более щедрый антифлуд (например, 30/10 мин на IP), чтобы не давать бесплатно долбить API.
3. Ключ дополнить cookie-идентификатором клиента в дополнение к IP, чтобы CGNAT и соседи по офису не блокировали друг друга. Cookie ставить только на странице формы, `SameSite=Lax`.
4. Тест: 5 невалидных заявок → 6-я валидная → `201`, а не `429`.

### M4. Привести деплой к одному пути

`deploy/avtotehservis.service:11` — `/var/www/avtotehservis/site`; `deploy/deploy.md:32-33` — `repo/site`; `scripts/backup.sh:6` — дефолт `/var/www/avtotehservis/site`.

**Сделать:** один путь во всех трёх файлах (рекомендую `/var/www/avtotehservis/repo/site`, как в инструкции), проверить, что `deploy.md` не противоречит сам себе в шагах обновления и бэкапа.

### M5. `http2 on;` не работает на целевых дистрибутивах

Директива появилась в nginx 1.25.1; Debian 12 — 1.22, Ubuntu 22.04 — 1.18, 24.04 — 1.24. `nginx -t` на них падает.

**Сделать:** заменить на `listen 443 ssl http2;` (работает и там, и там) либо явно требовать nginx ≥ 1.25.1 в `deploy.md`. Проверить конфиг на целевом дистрибутиве и записать версию nginx, на которой проверял.

### M6. Health-check не должен врать

`api/health.ts` делает `SELECT 1` и отдаёт `200 {"db":true}` на пустой базе, пока `/` отдаёт 500 — ровно та ситуация, в которую мы попали из-за Б1.

**Сделать:** использовать существующую `isMigrated()`; при отсутствии схемы — `503 {"status":"degraded"}`. Добавить в health проверку доступности каталогов данных и медиа на запись.

## 7. Как доказывать, что исправлено

В PR нужны не слова, а вывод команд. Приложи:

```bash
# 1. схема и маршрут в индексе
git ls-files site/migrations site/src/pages/media

# 2. чистая сборка и тесты
rm -rf node_modules dist .astro
npm ci && npm run typecheck && npm test

# 3. сайт поднимается с нуля
DATA_DIR=/tmp/x MEDIA_DIR=/tmp/xm npm run migrate
DATA_DIR=/tmp/x MEDIA_DIR=/tmp/xm npm run seed
DATA_DIR=/tmp/x MEDIA_DIR=/tmp/xm npm run start &
curl -s -o /dev/null -w '%{http_code}\n' localhost:4321/            # 200

# 4. фото открывается
curl -X POST localhost:4321/api/uploads -F file=@test.jpg
curl -sI localhost:4321/media/<id>/master.jpg | head -5              # 200 + immutable

# 5. кейс виден после публикации
curl -s localhost:4321/about | grep -c '<заголовок нового кейса>'    # ≥ 1

# 6. rate-limit не блокирует валидную заявку
# 5 × невалидная → 400, затем валидная → 201 (не 429)
```

**Правило:** цифры в README и в описании PR должны совпадать с тем, что реально даёт `npm test` на твоём коммите. «44/44» при 8/44 — это не мелочь: на таком отчёте строится решение о деплое.
