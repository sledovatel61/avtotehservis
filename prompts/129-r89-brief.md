## 2. Почему не в `/admin` (ключевое ограничение)

Админки на боевом домене **не существует**: `/admin/**` — SSR-маршруты, в статическую сборку GitHub Pages они не попадают вовсе (`export-pages.mjs` вырезает ссылки на `/admin`, `robots.txt` закрывает `/manage`).

Статьи сейчас лежат в SQLite (`news`), которую при каждой сборке создаёт `export-pages.mjs` → `migrate.ts` + `seed.ts` из `site/src/server/seed-data.ts`. Значит: **всё, что Паша сохранит через `/admin/news`, на боевой сайт не попадёт никогда** — база живёт только внутри процесса сборки. Ровно эту ошибку мы уже закрывали дважды (`/admin/cases`, `/admin/reviews`).

Поэтому источником статей «Полезного» становится **файл в репозитории**, а публикация = коммит через GitHub API из `/manage/`, как у цен, фото работ и отзывов. Это не «урезанная редактура»: Паша получает полный цикл (создать → черновик → фото → опубликовать → удалить), а сайт пересобирается сам за 1–3 минуты.

## 3. Целевая схема данных — `site/content/news.json`

Формат фиксируется здесь и обязателен для 130, 131, 132, 134. `version` и `updated_at` — как в `cases.json`/`reviews.json`.

```json
{
  "version": 1,
  "updated_at": "2026-11-21T09:00:00.000Z",
  "items": [
    {
      "slug": "remen-grm-kogda-menat",
      "title": "Ремень ГРМ: когда менять и почему «по регламенту» — не ответ",
      "seo_title": null,
      "excerpt": "Короткий лид для карточки и meta description.",
      "category": "sovety",
      "body_md": "Текст в Markdown…",
      "cover": null,
      "cover_static": "/img/news-1.svg",
      "status": "published",
      "published_at": "2026-11-18 10:00",
      "updated_at": "2026-11-18 10:00"
    }
  ]
}
```

Правила:

- `slug` — `^[a-z0-9-]{3,80}$`, уникален, **не меняется после первой публикации** (иначе рвётся URL и индексация).
- `seo_title` — `null` или строка ≤ 60. Если `null`, в `<title>` идёт `title` (обрезка — забота А5, не файла).
- `excerpt` — имя поля **не переименовывать** (его уже используют `news.astro`, `[slug].astro`): 120–200 символов рекомендуется, жёсткий предел 300.
- `category` — только из `NEWS_CATEGORIES` (`sezonnoe`, `sovety`, `servis`). Новые категории в этом круге не добавляем.
- `body_md` — Markdown, 200–40000 символов. Плейсхолдеры `{{price:КЛЮЧ}}` продолжают работать: в тексте они остаются как есть, подстановка — при рендере через `fillPrices` (как сейчас в `content.ts`).
- `cover` — `null` или объект `{ base, w, h, ext, alt }`:
  - файлы лежат в `site/public/media/news/<slug>/<base>-480.<ext>`, `…-960.<ext>`, `…-1600.<ext>`; превью для соцсетей — `<base>-og.jpg` (1200×630, всегда JPEG);
  - `base` — `^[a-z0-9]{4,12}-cover$`; `ext` — `webp` или `jpg`; `w`/`h` — размер 1600-варианта; `alt` — 3–160 символов, обязателен.
- `cover_static` — путь вида `/img/news-1.svg` для старых статей; взаимоисключающе с `cover` (проверять: либо одно, либо другое, либо ни одного → тогда фолбэк на `/img/news-1.svg`).
- `status` — `published` | `draft`. Черновики **остаются в файле** (Паша сохраняет их), но не попадают ни в страницы, ни в sitemap, ни в RSS.
- `published_at` / `updated_at` — `YYYY-MM-DD HH:MM` (как в сиде).

Статьи в `seed-data.ts` **не удалять** (сид — часть схемы, его трогать нельзя). Они навсегда остаются историческим источником; страницы читают только `news.json`.

## 5. SEO: что именно должно быть на странице статьи

Уже есть: `canonical` без query (проверено в `Base.astro`), `og:*`, `article:published_time`, `NewsArticle`, `BreadcrumbList`, `sitemap` с `lastmod`.

Добавляем:

1. `BlogPosting` вместо `NewsArticle` — раздел вечнозелёный, это статьи, а не новости. Поля: `headline`, `description`, `image` (обложка статьи), `datePublished`, `dateModified`, `inLanguage`, `author` и `publisher` = Organization с `logo`, `mainEntityOfPage`.
2. `og:image` / `twitter:image` = `<base>-og.jpg` статьи, а не общий `/img/og.png`; `article:modified_time`.
3. `title` из `seo_title`, иначе `title` + « — АвтоТехСервис»; `description` из `excerpt`.
4. `lastmod` в sitemap — из `updated_at`.
5. RSS `/news/rss.xml` (20 последних), `<link rel="alternate" type="application/rss+xml">` в `<head>`, ссылка в подвале.
6. Подписи раздела: `<title>`, `h1`-обвязка, крошки, JSON-LD крошек, `page-head` — «Полезное», не «Новости и акции».
7. Блок «Читайте также» — 3 статьи той же категории (уже есть `otherNews`, переключить на файл).
8. Верификация: `PUBLIC_GOOGLE_SITE_VERIFICATION` и `PUBLIC_YANDEX_VERIFICATION` → соответствующие `<meta>` в `<head>`, только если заданы. Без этого Google Search Console не подтвердить, а именно оттуда идёт гугл-трафик (GA сама по себе посетителей не приводит).

## 6. Метрика и согласие на cookies

**Порядок:** до согласия ни один сторонний запрос не уходит. Ни `mc.yandex.ru`, ни `googletagmanager.com`.

- Баннер (первый визит): короткий, внизу, две кнопки — «Принять все» и «Только необходимые», ссылка на политику. Выбор хранится в `localStorage` (`ats_consent_v1`) и в cookie `ats_consent` (180 дней, `SameSite=Lax`), повторно не спрашиваем; ссылка «Настройки cookies» в подвале открывает баннер снова.
- «Только необходимые» = счётчики не грузятся вообще, сайт работает полностью.
- «Принять все» = грузим Метрику (`PUBLIC_YM_ID`) и GA4 (`PUBLIC_GA_ID`), если они заданы. Если переменная пуста — счётчика нет в HTML в принципе.
- `/manage/` и `/admin` из счётчиков исключаются (у `/manage` своя статика, у `/admin` — `X-Robots-Tag`); в Метрике — по `data-page` / пути.
- CSP в `middleware.ts` расширяется **условно**: домены счётчиков добавляются только если ID задан. Без ID политика остаётся строгой, как сейчас.
- Политика: §6 `privacy.astro` переписывается (перечень: Метрика — ООО «ЯНДЕКС», РФ; GA — Google LLC, США, трансграничная передача), добавляется раздел про отзыв согласия и про то, что до согласия счётчики не загружаются.
- **Версию согласия формы (`consent_version`) не трогать.** Она сверяется с `relay/wrangler.toml` (`relay-smoke.yml`), и её смена ломает все заявки. Для политики вводится отдельное поле `policy_version` — его печатает только `/privacy`.
- Гейт `check-analytics.mjs`: без ID в `pages-dist` нет ни `mc.yandex`, ни `ym(`, ни `gtag`; с ID счётчик есть на `/`, `/otzyvy/`, `/news/` и на статье; баннер есть всегда, кроме `/manage`.

## 7. Обложка статьи (фото)

- Загрузка в редакторе — тем же браузерным конвейером, что фото работ (`editor.js`: `decode` → кроп → 480/960/1600 webp). Ничего не отправляем на сервер.
- Дополнительно из того же кадра делается `og.jpg` 1200×630 (кроп 16:9, качество 0.82) — для Telegram, VK, Twitter и Google Discover.
- Одно фото = карточка в списке + герой статьи + `og:image` + `image` в `BlogPosting`. Несколько фото внутри текста — следующий круг, в этот не тащим.
- Требования к исходнику: JPEG/PNG/WebP/HEIC, до 15 МБ, минимум 1200 px по длинной стороне (иначе предупреждение «фото будет мыльным в превью»).

## 8. Что остаётся владельцу (не блокирует код)

1. Создать счётчик Яндекс.Метрики → прислать номер (`PUBLIC_YM_ID`).
2. Создать ресурс GA4 → прислать `G-…` (`PUBLIC_GA_ID`).
3. Google Search Console: подтвердить домен (мета-тег через `PUBLIC_GOOGLE_SITE_VERIFICATION`), отправить `https://ats-rostov.ru/sitemap.xml`.
4. Яндекс.Вебмастер: то же (`PUBLIC_YANDEX_VERIFICATION`), регион — Ростов-на-Дону.
5. После подключения — проверить баннер cookies в приватном окне и «Только необходимые».
