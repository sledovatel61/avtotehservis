## 7. Форма записи

Пять экранов, как в мокапе. Валидация на клиенте — для удобства, на сервере — обязательна и независима.

| Экран | Поля | Правила |
|---|---|---|
| 1. Авто | марка (поиск + свободный ввод), модель, год, VIN, пробег | марка обязательна; год 1980–2026; VIN 17 символов, запрещены I/O/Q; пробег 0–2 000 000 |
| 2. Что нужно | чипы услуг, «не знаю — нужна диагностика», до 3 фото | минимум услуга или «не знаю»; фото ≤ 15 МБ каждое |
| 3. Когда | 14 дней, слоты 09:00–19:00, «как можно раньше» | дата не в прошлом, слот не занят; занятость — из БД |
| 4. Контакты | имя, телефон, канал связи, согласие | телефон 11 цифр; согласие не предустановлено |
| 5. Сводка | всё выбранное + «Отправить» | правка любого шага без потери данных |

**Поведение:**

- «Далее» неактивна, пока шаг невалиден; ошибки — под полем, фокус на первое; `aria-describedby`, `aria-invalid`;
- черновик в `localStorage`, если доступен; при ошибке отправки данные не теряются;
- идемпотентность: `idempotency_key` (uuid v4) живёт в черновике; повторная отправка возвращает тот же номер;
- после успеха — талон `A-DDMM-XXXX`, «что дальше», «что взять с собой», кнопка «Добавить в календарь» (`.ics` генерируется на клиенте, без внешних сервисов);
- телефон в ошибке — `+7 (928) 906-57-00`;
- согласие: чекбокс + ссылка на `/privacy` + фиксация версии политики;
- honeypot-поле и минимальное время заполнения — тихо игнорировать бота;
- e-mail у клиента не спрашиваем.

**API:**

```
POST /api/uploads        multipart, 1 файл → {id, url, width, height}
GET  /api/slots?date=…   → {date, slots:[{time, available}]}
POST /api/leads          JSON → 201 {ticket, lead_id, status:"accepted"}
```

Ошибки: `400` с `{error:{code, message, fields}}`, `409 slot_taken` + свободные слоты, `413` слишком большой файл, `429` слишком часто. Ответ — всегда JSON, без HTML-страниц.

Payload:

```json
{
  "name": "Иван",
  "phone": "+79289065700",
  "contact_method": "call",
  "car": {"brand": "Лада (LADA)", "model": "Vesta", "year": 2019, "vin": null, "mileage": 84000},
  "services": ["to-maslo"],
  "preferred": {"date": "2026-10-24", "slot": "10:00", "asap": false},
  "photos": ["upl_…"],
  "consent": true,
  "consent_version": "2026-10-21",
  "page": "appointment",
  "idempotency_key": "uuid-v4",
  "honeypot": "",
  "form_started_at": 1761000000000
}
```

## 8. Заявки: доставка и ноль потерь

1. `POST /api/leads` в одной транзакции: валидация → `INSERT leads` (UNIQUE по `idempotency_key`) → `INSERT outbox` (2 строки: telegram, email) → `201 {ticket}`.
2. Клиент видит номер **до** доставки. Заявка уже в БД — источник истины.
3. Воркер (интервал 30 с + при старте) забирает `pending` и `failed` с `next_attempt_at <= now`, отправляет, пишет статус.
4. Ретраи: 1 мин → 5 мин → 30 мин → 2 ч → 6 ч, максимум 8 попыток, потом `failed` и красный бейдж в админке.
5. Telegram упал — письмо всё равно уходит; упали оба — заявка в БД и в админке, доставка догоняет.
6. В админке — кнопка «Отправить ещё раз» и история попыток с текстом ошибки.
7. Telegram: HTML-сообщение с номером, именем, телефоном, авто, услугами, датой/слотом, ссылкой на заявку в админке. Токен и `chat_id` — только env.
8. E-mail: SMTP, тема с номером заявки, текстовое и HTML-тело, ссылка на заявку. Адрес получателя — из настроек.
9. `TELEGRAM_API_BASE` и `SMTP_*` должны позволять подменить транспорт в тестах на локальную заглушку. Это требование, а не пожелание: без него ревьюер не сможет проверить доставку.
10. Логи — структурные, без полного телефона (маскировать), с номером заявки.

**Обязательные тесты доставки:** Telegram недоступен → письмо ушло; SMTP недоступен → Telegram ушёл; оба недоступны → две записи `pending`, заявка видна, ручной ретрай работает; повторный POST с тем же ключом → тот же номер, второй заявки нет.

## 9. Админка

Вход: `/admin/login`. Один администратор (роль `owner`), создаётся командой `npm run admin:create`; пароль ≥ 12 символов, хеш scrypt с солью; смена пароля в настройках. Сессия — httpOnly, Secure, SameSite=Lax, 7 дней, токен в БД хешем; выход; ограничение попыток входа.

| Раздел | Возможности |
|---|---|
| Дашборд | новые заявки, просроченные доставки, черновики кейсов, последние действия |
| Заявки | список с фильтрами (статус, дата, канал), карточка, фото клиента, смена статуса, повторная доставка |
| Кейсы | создание за 3 шага (≤ 5 действий), фото/видео, обложка, alt, услуга, черновик/публикация, скрытие |
| Новости | Markdown + превью, категория, обложка, публикация, удаление |
| Отзывы | добавление, модерация, источник и ссылка, публикация/скрытие |
| Услуги | тексты, порядок, SEO-поля, скрытие |
| Настройки | телефоны, часы, адрес, Telegram, e-mail, рейтинги (вкл/выкл), юрлицо |
| Медиа | библиотека, размеры, удаление неиспользуемого |
| Журнал | кто, что и когда изменил (без паролей и токенов) |

**Мобильная публикация ≤ 60 секунд.** Сценарий: «Новый кейс» → камера/галерея (мультивыбор) → заголовок → «Опубликовать». Не больше 5 действий, не больше 2 обязательных полей (заголовок + минимум одно медиа). Автослаг, услуга по умолчанию, alt можно заполнить позже (но подсказка). Прогресс загрузки, отмена, повтор при обрыве. Проверка — на 390 px и на реальном телефоне владельца.

**Безопасность админки:** CSRF-токен на все изменяющие запросы, проверка `Origin`, rate-limit, `noindex`, отдельный layout, никаких публичных ссылок на админку, загрузки только через серверную валидацию, аудит действий.

## 10. Медиа

- Фото: JPEG/PNG/WebP/AVIF, ≤ 15 МБ, до 3 на заявку и до 12 на кейс. `sharp`: авто-поворот, удаление EXIF (включая GPS), ресайз до 2000 px, варианты 480/960/1600 в WebP + AVIF + JPEG-fallback.
- Видео: MP4/WebM, ≤ 100 МБ, ≤ 3 мин. Постер обязателен, если ffmpeg недоступен; если доступен — кадр генерируется автоматически. Range-запросы, `preload="none"`, без автоплея со звуком.
- Имена файлов — случайные, без пользовательских строк; хранение вне `public/`; выдача через контролируемый маршрут с кеш-заголовками; исполняемые файлы и SVG от пользователей не принимаются.
- Неиспользуемые загрузки чистятся через 24 ч; удаление медиа — только если не привязано к опубликованной сущности.
- `DATA_DIR` и `MEDIA_DIR` — вне репозитория; в git медиа не попадают.

## 12. Безопасность и 152-ФЗ

- Секреты только в env: `BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `SMTP_HOST/PORT/USER/PASS`, `MAIL_TO`, `MAIL_FROM`, `SESSION_SECRET`, `PUBLIC_SITE_URL`, `DATA_DIR`, `MEDIA_DIR`. В git — только `.env.example` без значений.
- Пароли — scrypt, сессии — хеш токена, CSRF на изменяющих запросах.
- Rate-limit: заявки 5/час с IP, загрузки 30/час, вход 5/15 мин.
- Заголовки: CSP (`default-src 'self'`; без `unsafe-eval`; inline-стили — только если неизбежно, с nonce/hash), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors 'none'`.
- Валидация и нормализация всех входов, экранирование вывода, защита от SQLi (prepared statements), path traversal, XSS, подмены MIME (проверка сигнатур).
- ПД: минимум данных, согласие с версией и временем, срок хранения в политике (1 год), удаление по запросу, журнал доступа, IP — только хешем.
- Бэкапы: ежедневно SQLite + медиа, хранение 14 дней, скрипт восстановления **проверен** на копии.
- Политика конфиденциальности — полный текст на `/privacy`; пометить, что требует проверки юристом.

## 13. Тесты

`npm test` должен проходить без сети и без реальных Telegram/SMTP.

**Unit:** валидация (телефон всех форматов, VIN с I/O/Q, год, пробег, слоты, дата, услуги из whitelist, согласие), формат и уникальность номера, идемпотентность, бэкофф outbox, парсинг настроек, санитайз Markdown.

**Интеграционные (временная БД + поднятый сервер):**

- полный сценарий заявки → 201 → запись в `leads` → две строки `outbox`;
- повтор с тем же ключом → тот же ticket, одна заявка, две строки outbox;
- заглушка Telegram падает → email `sent`; заглушка SMTP падает → telegram `sent`; оба падают → обе `pending`, затем ретрай;
- занятый слот → 409 со свободными;
- невалидные поля → 400 с перечнем;
- 413 на большом файле, 429 на спаме;
- вход в админку: неверный пароль, блокировка после N попыток, CSRF-отказ;
- черновик кейса не виден публично; публикация видна; скрытие убирает;
- 404 на несуществующую услугу/новость.

**Ручные проверки:** пройди форму на 390 px, проверь клавиатуру, reduced-motion, загрузку фото с телефона (если есть устройство — иначе честно пометь).

Отчёт о тестах — в `site/README.md`: что запускалось, что прошло, что не проверено.

## 14. Деплой и эксплуатация

Цель — VPS в РФ (Beget, 2 ядра / 2 ГБ — ориентир из `docs/05`), Debian/Ubuntu, nginx + systemd + Let's Encrypt.

В `site/deploy/`:

- `nginx.conf`: reverse proxy на `127.0.0.1:4321`, `client_max_body_size 110m`, таймауты под загрузку видео, кеш статики, gzip;
- `avtotehservis.service`: `Restart=always`, `EnvironmentFile=/etc/avtotehservis/env`, отдельный пользователь, `NoNewPrivileges`, `ProtectSystem`;
- `backup.cron` и `backup.sh`/`restore.sh`;
- `deploy.md`: установка с нуля, миграции, создание админа, TLS, обновление, откат, восстановление из бэкапа, где лежат логи.

Требования:

- приложение не работает от root; БД и медиа — в `/var/lib/avtotehservis`;
- миграции — отдельной командой, не автоматически при старте;
- health-check `/api/health` (без секретов) для мониторинга;
- логи — в journald, без ПД;
- откат: предыдущий коммит + пересборка; миграции совместимы вперёд;
- `deploy.md` должен быть воспроизводим: ревьюер пройдёт по нему на чистой машине.

Домен пока не зарегистрирован. В конфиге — `PUBLIC_SITE_URL` из env; для тестов — `http://localhost:4321`. Не вписывай `avtotehservis.ru` как рабочий адрес: он занят.
