## 1. Блокер: пустые рейтинги роняют `/` и `/about` в 500

**Воспроизведено через админку, не через SQL:**

1. `/admin/settings` → очистить три поля «Источник» → «Сохранить» → `302 …Настройки сохранены`.
2. `ratings` в БД = `[]`.
3. `GET /` → **500**, `GET /about` → **500**.
   Лог: `TypeError: Cannot read properties of undefined (reading 'url')` — `index.astro:256`, `about.astro:136`.

**Почему блокер.** Очистить неподтверждённые рейтинги — ровно то, чего требует задание (§6: рейтинги скрыты, пока владелец не подтвердил). То есть штатное действие владельца убивает главную страницу. `health` при этом отдаёт 200, тесты — 48/48: система выглядит здоровой и не работает.

**Дополнительно (хуже, чем в ревью):** после сохранения форма настроек рендерит **ноль строк рейтингов**, потому что строки берутся из `S.ratings.map`. Вернуть рейтинги через админку нельзя — только правкой БД.

**Что сделать:**

1. `index.astro:256`, `about.astro:136` — не разыменовывать первый элемент: `S.ratings[0]?.url ?? S.map_link`. Для пустого состояния отзывов лучше общий компонент, но не обязательно.
2. `/admin/settings` — форма всегда показывает **три строки** рейтингов, включая пустые (рендер по фиксированному `[0,1,2]`, а не по `S.ratings`), чтобы данные можно было вернуть.
3. В обработчике сохранения — не терять строку, если заполнена хотя бы ссылка (сейчас фильтр только по `source`).
4. **Тест:** `settings.ratings=[]` → `GET /` и `GET /about` = 200; сохранение формы с пустыми источниками → 302 и страницы живы.

## 2. Major: обложку опубликованного кейса можно удалить из библиотеки

**Воспроизведено полностью через UI:**

```
1. загрузить фото → /api/uploads  (attached_to = NULL)
2. в опубликованном кейсе нажать «Сделать обложкой»
   → cases.cover_media_id установлен, media.attached_to остаётся NULL
3. /admin/media → «Удалить» это фото → 302 «Медиа удалено»
```

Итог: строки `media` нет, файлы с диска удалены, `cover_media_id` молча обнулён, на сайте — заглушка. Ошибки или предупреждения владелец не видит.

Защита работает только для медиа, загруженного через карточку кейса (`attached_to='case:N'`), — значит, дыра локальная.

**Что сделать (любой из вариантов, лучше оба):**

1. В действии `cover` (`admin/cases/[id].astro`) писать `UPDATE media SET attached_to='case:<id>' WHERE id=?` и снимать привязку у прежней обложки.
2. В `canDelete` (`admin/media/index.astro`) добавить проверку по факту использования:
   `EXISTS(SELECT 1 FROM cases WHERE cover_media_id=? AND status='published')` — и то же для `news`.
3. **Тест:** обложка published-кейса, взятая из библиотеки → `POST action=delete` отклонён, `media` и файл на месте.

## 3. Major: квота и антифлуд обходятся подменой cookie

**Воспроизведено:**

```
8 заявок, 8 разных ats_cid → 201 × 8  (в БД +8)
7 заявок, одна ats_cid     → 201 × 5, затем 429 × 2
```

Ключ — `ip|cid`, где `cid` полностью подконтролен клиенту. Требование было «**дополнить** ключ cookie к IP», а получилось «заменить IP на cookie»: достаточно присылать новый `Cookie` на каждый запрос.

**Что сделать:** два независимых уровня, считать оба.

| Уровень | Ключ | Лимит | Назначение |
|---|---|---|---|
| Жёсткий | только `hash(ip)` | `RATE_LIMIT_LEADS_IP` = 30/час; антифлуд 60/10 мин | бот за NAT не обойдёт |
| Мягкий | `hash(ip)|cid` | 5/час (как сейчас) | соседи по офису не мешают друг другу |

`ats_cid` должен ставиться сервером на страницах форм (уже ставится) — не доверять произвольному значению из запроса как единственному ключу.

**Тест:** 10 валидных заявок с 10 разными `ats_cid` → после N-й `429`; и отдельно — 5 обычных заявок с одной cookie по-прежнему проходят.
