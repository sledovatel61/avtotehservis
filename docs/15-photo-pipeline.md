### 2.1. Архитектура: контент кейсов — файлы в репозитории

#### 2.1 Хранение

```
site/content/cases.json                     ← описание кейсов (в git)
site/public/media/cases/<slug>/<id>-<phase>-<width>.webp
                                            ← фото (в git, отдаются как /media/…)
site/src/shared/cases-schema.ts             ← типы + разбор/валидация JSON (общие для сайта и админки)
site/src/server/cases-store.ts              ← чтение cases.json на сборке, фолбэк на seed
```

- В репозиторий кладём **только производные 480 / 960 / 1600 WebP**. Оригиналы и мастер 2000 px
  не храним: их место — у владельца. AVIF для фото не делаем (браузер не умеет кодировать),
  поддержка WebP — 97 %+.
- Средний вес одного кадра: 1600 ≈ 250–350 КБ, 960 ≈ 120 КБ, 480 ≈ 40 КБ → **≈ 450–500 КБ на фото**.
- Кейс из 6 фото ≈ 3 МБ. 100 кейсов ≈ 300 МБ. Это влезает, но нужен бюджетный гейт (см. §5).
- `.gitignore` сейчас содержит `media/` — он глушит и `site/public/media/`. Нужно исключение.

#### 2.2 Формат `cases.json`

```json
{
  "version": 1,
  "updated_at": "2026-11-17T16:00:00Z",
  "cases": [
    {
      "slug": "pores-po-bokovine",
      "title": "Порез по боковине: осмотрели и сказали прямо",
      "description": "Колёса · ремонт колеса R17 — 800 ₽ или замена шины, если ремонт небезопасен.",
      "service_slug": "balansirovka",
      "mode": "before_after",
      "status": "published",
      "published_at": "2026-11-17",
      "sort": 10,
      "cover": "ab12cd/after-1600.webp",
      "before": [{ "id": "ab12cd", "alt": "Порез на боковине до ремонта", "w": 1600, "h": 1200 }],
      "after":  [{ "id": "ef34gh", "alt": "Тот же участок после вулканизации", "w": 1600, "h": 1200 }],
      "photos": []
    }
  ]
}
```

- `mode`: `single` (одна фотография работы) или `before_after` (пары «до / после»).
- `cover` и `id` — относительные имена внутри `media/cases/<slug>/`, без `/media/` и без ширины:
  ширина подставляется при рендере (`<id>-<phase>-480|960|1600.webp`).
- Все фото кейса — один массив `before`/`after`/`photos`, порядок = порядок в массиве.
- Пустой или отсутствующий `cases.json` → сайт работает как сейчас (сид-кейсы + `CASE_COVERS`),
  то есть **обратная совместимость обязательна**.

#### 2.3 Как фото попадают в git — два варианта

**Вариант A. Локальная админка + кнопка «Опубликовать».**
Админка как сейчас (`npm run dev` на компьютере), sharp делает варианты, кнопка коммитит
файлы и `cases.json` в `preview/github-pages` через GitHub API по токену.
Плюсы: максимальное качество (sharp, AVIF при желании), привычный код, меньше нового.
Минусы: владельцу нужно поставить Node, склонировать репозиторий, держать его обновлённым.

**Вариант B. Админка прямо на Pages, в браузере (рекомендуется).**
Отдельная страница `/manage/` (не `/admin/` — этот каталог запрещён гейтом в экспорте):
вход по личному токену GitHub (fine-grained, только этот репозиторий, Contents: write),
дальше всё в браузере: выбор файлов и перетаскивание, обработка через canvas
(автоповорот по EXIF, кроп, поворот, оттенки), три размера WebP, коммит через Git Trees API
одним коммитом вместе с `cases.json`.
Плюсы: работает с телефона, ничего ставить не нужно, фото сразу на сайте через 1–2 минуты.
Минусы: качество кодирования чуть хуже sharp, AVIF недоступен, токен хранится в браузере
(localStorage) — нужна аккуратность: только fine-grained токен на один репозиторий,
страница без сторонних скриптов, `noindex` + `Disallow: /manage`.

Важная техническая деталь: `export-pages.mjs` публикует **только маршруты из `sitemap.xml`**
и копирует `dist/client` целиком. Значит:
- страницы кейсов обязаны попасть в `sitemap.xml.ts`, иначе их физически не будет на Pages;
- `/manage/` не нужно никуда добавлять: это статичный каталог `site/public/manage/`,
  он уезжает вместе с `dist/client` без единой правки экспортёра (править его запрещено).
  Внутри — обычные `<script>` без сборки, относительные пути (`./app.js`), чтобы работало
  под префиксом `/avtotehservis/manage/`.
- `media/` попадает на Pages так же: файлы лежат в `site/public/media/…`, экспортёр уже
  переписывает `/media/…` в HTML, CSS и JS под base.

Смешивать оба варианта в одном круге не нужно: получатся две правды о кейсах.

### 3.1. Админка: что должно быть удобно

#### 3.1 Экран кейса

- Список кейсов: обложка, название, статус (черновик/опубликован), число фото, дата.
- Карточка кейса: название, слаг (авто, можно поправить), описание, услуга, дата, статус.
- Переключатель режима: **«Одно фото работы»** / **«До и после»**.
- В режиме «до и после» — две зоны: **«Как было»** и **«Как стало»**; перетаскивание файлов
  в нужную зону и перенос фото между зонами.
- В режиме «одно фото» — одна зона «Фотография работы», без дележа.
- Обложка: выбрать из загруженных (по умолчанию первая из «как стало»).
- Порядок фото: перетаскивание, стрелки для телефона.
- Подпись (alt) у каждого фото — обязательна, с подсказкой «что видно на снимке».

#### 3.2 Минимальный набор инструментов при загрузке

1. Автоповорот по EXIF (снимок с телефона не лежит на боку).
2. Кроп: свободный + пресеты 4:3, 1:1, 3:4, 16:9; сетка третей.
3. Поворот на 90° влево/вправо.
4. Выравнивание горизонта: ползунок ±15°.
5. Масштаб и «сбросить».
6. Живой предпросмотр в трёх размерах и счётчик «уйдёт в репозиторий: N фото, M МБ».
7. Очередь: прогресс по каждому файлу, возможность убрать до публикации.

Не делаем (сознательно): цветокоррекцию, ретушь, водяные знаки, шаблоны, пакетные пресеты.

#### 3.3 Публикация

- Кнопка **«Опубликовать»**: один коммит (файлы + `cases.json`) в `preview/github-pages`.
- Статус сборки: «отправлено → собирается → сайт обновлён» со ссылкой на страницу кейса.
- Если сборка упала — сайт остаётся на прошлой версии (Pages не публикует битую сборку),
  в админке показываем ссылку на лог workflow.
- Удаление фото — тем же коммитом (файлы удаляются, а не остаются сиротами).
- Черновик (`status: draft`) коммитится, но не рендерится на сайте.

### 8.1. Ограничения и риски

- Токен в браузере — только fine-grained, только этот репозиторий, Contents: write, срок 90 дней.
  Страница без стороннего JS, `noindex`, `Disallow: /manage`; кнопка «Выйти» стирает токен.
- Коммит в `preview/github-pages` — рабочая ветка превью; боевой сайт позже переедет

  как «вариант A».
