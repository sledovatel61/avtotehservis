## Гейты: что ловят и как чинить

- **`check-media-budget.mjs`** обходит `site/public/media`, исключает `.gitkeep`, проверяет пары вариантов 480/960/1600, каталоги кейсов без записи в JSON и файлы тяжелее 800 КБ. При 400 МБ предупреждает, при 700 МБ завершает работу с ошибкой. В обычном режиме печатает сводку папка/число файлов/МБ; `--json` выводит машинный отчёт.
- **`check-cases.mjs`** использует `parseCasesFile` из общего контракта. Дополнительно сверяет версию и форму JSON, режимы `single`/`before_after`, ссылки и размеры вариантов на диске, alt и отсутствие опубликованной страницы черновика. Размеры читает через уже установленный `sharp`; для 480/960 ожидаемые пиксели пересчитывает из длинной стороны исходного 1600-варианта.
- **`check-pages.mjs`** после статической сборки проверяет доступность `/manage/` без индексации и маршрут/разметку каждого опубликованного кейса.

При ошибке исправлять данные кейса или набор вариантов, затем повторять гейт; не обходить ошибки удалением проверок.

## Тесты: список кейсов

В `photo-pipeline.test.ts` проверяются: валидный минимальный JSON; удаление испорченного фото при пустом alt, неправильном base и размерах ≤0; поведение парсера при `single` с кадром в `before`; точные `photoPath`/`srcset` для WebP и JPG; приоритет обложки; сортировка; совпадение `LIMITS` админки с фактическими границами парсера; битый JSON без исключения, фильтр draft и инвалидирование кэша по mtime; три варианта медиа, файл 900 КБ, отсутствующая ширина и пороги 400/700 МБ; реальные размеры WebP и запрет показа draft.

Тесты создают файлы только во временных каталогах, `site/public/` не меняют и повторный `npm ci` не вызывают.

## Найденные расхождения с контрактом / исходниками

1. Указанный в задании `docs/15-photo-pipeline.md` отсутствует в ветке preview; вместо него присутствуют `docs/17-photo-admin-dev-notes.md`. Документ №15 не создавал и не переименовывал. Проверить его на расхождения имён/полей невозможно; текущую документацию сверял по `cases-schema.ts`, `cases-store.ts` и файлам админки.
2. `parseCasesFile` валидирует поля и отбрасывает испорченные фото, но сам не отклоняет межполевое противоречие `mode: single` + кадр в `before`. Админка проверяет режим при сохранении; здесь это дополнительно закрыто `check-cases.mjs` и тестом, запрещённые файлы не менялись.
3. Константы лимитов в схеме не экспортируются. Тест импортирует `LIMITS` из `site/public/manage/store.js` и сопоставляет их с граничным поведением `parseCasesFile`: title 5–90, description 0–200, alt 3–160, slug 3–60 — совпадают.
4. В корневом `.gitignore` есть общий шаблон `media/`, поэтому одного `/media/` в `site/.gitignore` недостаточно для `site/public/media`. Добавлены локальные исключения `!public/media/` и `!public/media/**`, корневой файл не тронут. `git check-ignore -q site/public/media/cases/demo/demo-after-960.webp` возвращает 1 (путь не игнорируется); `-v` показывает совпавшее отрицательное правило `!public/media/**`, а не запрещающий шаблон.
