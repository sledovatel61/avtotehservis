Вариант A не изменился побитово: силуэта в нём нет, профиль не участвует — это контроль

- Худший тир статически **954.1 ≤ 1035.1** → допуск выполнен, запас 81 оп/px (7.8 % лимита).
- К аршину 941: **+1.4 %** при допуске +10 %. Совпадает с A11 владельца (779.9/821/954.1)
  и с числами, зашитыми в `gate.ts` ([780, 821, 954]).
- Динамически худший тир **852.3 — на 9.4 % дешевле «до»**: if-лесенка `pTop` на практике
  проходит 2–4 сравнения из десяти, а `pBottom` вне базы выходит рано; статическая модель
  считает все ветви подряд и потому консервативна. Динамика — не замена гейту, а второе,
  независимое число: гейт держится на статике.

Разбивка стоимости обращения к профилю (`bg3d-after.json`, `profileCost`):

| модель | inst | scalar | комментарий |
|---|---|---|---|
| динамика, среднее по сетке 64×64 | 54.0 | 62.0 | по x от 50 до 59 inst: лесенка проходит разное число сравнений |
| статика (все ветви подряд), мой подсчёт | 131 | 139 | |
| статика + обвязка `carSdf` (4/4) | 135 | 143 | |
| принятая константа `PROFILE_COST` | 145 | 130 | pTop 101 + pBottom 17 + pArch×2 10 + carProfile 12 + carSdf 5 (SPIR-V byFunc) |

Расхождение 135/143 против 145/130 — разные конвенции счёта, а не ошибка: SPIR-V относит
часть операций `pTop` к композитным и ветвлениям (у меня они в inst), а скалярная модель
разворачивает векторные операции по компонентам (отсюда scalar > inst у меня и scalar < inst
у владельца). Обе модели самосогласованы: мой статический пересчёт сходится с SPIR-V по
листам (`bg3d-shader-check.mjs`), динамический — с геометрией модуля (20 000 точек, Δ ≤ 9e-16).
