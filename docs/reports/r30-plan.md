## 2. Разбор: что значит «настоящий 3D» и чем это отличается от SVG

Сейчас заставка — это **2D-графика**: `stroke-dashoffset` по путям SVG, шторки на `translate3d`.
Браузер рисует линии, глубины нет: нет камеры, нет перспективы, нет объёма, нет
самосветящихся поверхностей. Любые «улучшения» этого подхода останутся плоскими —
именно поэтому владелец видит «нарисованную машинку».

Реальный 3D в браузере = **WebGL2** (или WebGPU, но он есть не везде). Три варианта
технически:

| Вариант | Что даёт | Вес | Риск |
|---|---|---|---|
| **A. Свой шейдер (raymarching/SDF)** | неоновый контур кузова реально в 3D: камера облетает, линии живут на поверхности, свечение и bloom считаются в шейдере | **12–25 КБ gzip**, без библиотек | требует аккуратной математики; сложно заставить выглядеть «как машина», если SDF грубый |
| **B. three.js + экструдированный знак/силуэт** | быстрый старт, готовые материалы, свечение, постобработка | **409 КБ gzip** (проверено: `three.module.js` 126 КБ + `three.core.js` 283 КБ, r187) — даже с tree-shaking ~90–120 КБ | тяжело для 2,5-секундной заставки; на мобильном интернете убивает смысл |
| **C. CSS 3D (`rotateY`, `translateZ`)** | объём без WebGL, ноль зависимостей | 0 КБ | это не «настоящий 3D-эффект»: нет перспективной геометрии модели, максимум — карточки в пространстве |

**Вывод для заставки:** идём вариантом **A** — свой WebGL2-шейдер. Он единственный даёт
одновременно «настоящий 3D», малый вес и неоновую эстетику, о которой сказал владелец
(«неоновыми эффектными линиями нарисовался бы силуэт авто в 3D»). three.js не тянем:
409 КБ на входную анимацию — это дороже, чем весь остальной раздел (HTML 9,9 + CSS 6,1 + JS 1,4 КБ).

### Проверено в этой песочнице (факты, не оценки)

- **WebGL2 работает** в тестовом Chromium: `WebGL 2.0 (OpenGL ES 3.0)`,
  рендерер `ANGLE (SwiftShader)`, `MAX_TEXTURE_SIZE = 8192`, пиксель из `readPixels` читается.
  Значит скриншоты-доказательства и автотесты заставки возможны прямо в CI.
- **Скорость в CI не показатель:** тяжёлый фрагментный шейдер (40 итераций на пиксель)
  на программном SwiftShader при 1280×800 даёт **22,9 fps**. Это софтверный рендер,
  на реальной видеокарте тот же шейдер уйдёт в 60 fps с большим запасом, но **проверять
  плавность придётся на живом устройстве** — в задании агенту это прописано.
- **Бюджеты страницы сейчас:** HTML 9,9 КБ gzip, CSS раздела 6,1 КБ, JS заставки 1,4 КБ,
  кадр героя 27 КБ (avif). Заставка на 25 КБ — это +19 % к весу раздела, приемлемо.

## 3. Разбор: реализуем ли 3D-фон на странице

Владелец просил «рассмотреть, насколько реализуемо». Короткий ответ: **да, но не как
«3D на всю страницу»**. Причины и рамки:

| Вопрос | Ответ |
|---|---|
| Что реально хорошо смотрится в фоне | медленный дрейф неоновой сетки/частиц в глубине, световая «пыль» в луче лампы, очень медленный параллакс по скроллу. Полноценная 3D-модель машины в фоне — нет: она спорит с фотографиями и текстом |
| Сколько стоит | один fullscreen-шейдер: **6–14 КБ gzip**, 1 canvas, 0 текстура (всё процедурное) |
| Бюджет кадров | рисовать в 0,5× разрешении и растягивать (неотличимо для мягкого фона), DPR ≤1,5, ≤8 draw-call'ов, пауза вне вьюпорта и при `document.hidden` |
| Когда выключать | `prefers-reduced-motion`, `navigator.connection.saveData`, батарея ниже 20 % (Battery API там, где есть), «слабые» устройства (`hardwareConcurrency ≤ 4`), и всегда — по кнопке «выключить фон» (сохраняется в localStorage) |
| Мобильные | тот же шейдер с ×0,5 итераций; либо статичный градиент, если fps < 40 на первых 60 кадрах (автоотключение) |
| Риск для текста | фоновый слой **не должен** ложиться под текст без подложки: контраст уже проверяется гейтом (`measure-contrast.mjs`), фон живёт только в «пустых» зонах секций |
| Что дороже всего | не сама графика, а дисциплина: пауза/возобновление, отключение, отсутствие утечек при переходах между страницами |

**Вывод:** 3D-фон делаем как **эксперимент с двумя вариантами и честными замерами** —
решение принимает владелец по кадрам и цифрам fps, а не «по ощущениям агента».
