## 1. Дефект 1: разрешение 1:1 (было 855×460 при 1425×767)

**Причина.** Пиксельный бюджет резал сцену ДО первого кадра, по паспорту GPU:

```
engine.resize():  scale = min(cfg.renderScale, budgetScale) * stress
                  budgetScale = fitScale(... opsPerPx × cssW × cssH × dpr², бюджет high 60 Гоп/с)
gate.decideTier(): renderScale = 0,9 / 0,75 / 0,6 по тиру + «площадь кадра» до 1,35·1920×1080
```

На 1425×767 при dpr 1 это давало `0,60` → **855×460**; при dpr 2 — **1810×974** вместо
2850×1534. Сцена была мутной на железе, которое тянет полное разрешение, а
«адаптивность» опиралась на догадку, а не на измерение.

**Что сделано.**

| где | было | стало |
|---|---|---|
| `gate.ts` | `renderScale` 1,0 / 0,9 / 0,75 / 0,6 по тиру + резка «площади кадра» | `renderScale = 1.0` всегда; в `reasons` — «разрешение 1:1 (css×dpr, dpr ≤ 2); понижение — только по факту падения fps» |
| `gate.ts` | `dprCap` 1,25 / 1,5 у mid/low | `dprCap = 2` на всех тирах |
| `engine.resize()` | бюджет режет `scale` на каждом resize | `scale = fpsScale × stress`; 1:1 по умолчанию. `budgetScale` включается **только после** того, как watchdog уже снизил `fpsScale` |
| `engine.watchdog()` | понижал `cfg.renderScale` при fps < 0,7·цели | понижает собственный `fpsScale` (1 → 0,75 → 0,5) при fps < 0,75·цели, пишет `fpsAtDegrade` и `degradations` |

Порог 0,75 — из допуска задания 0,5…1,0: при 60 к/с понижение начинается на 45 к/с.

**Замер на живом кадре** (Chromium 131 + SwiftShader, `/voyah-free?intro=0`, поля `live.json`):

| вьюпорт | CSS-хост | было | стало | требование |
|---|---|---|---|---|
| 1440×900, dpr 1 | 1425×767 | 855×460 (0,60) | **1425×767** | 1425×767 |
| 1440×900, dpr 2 | 1425×767 | 1810×974 (0,75) | **2850×1534** | 2850×1534 |
| 390×844, dpr 1 | 375×565 | 225×339 | **375×565** | 375×565 |
| 390×844, dpr 2 | 375×565 | — | **750×1130** | 750×1130 |

Проверка встроена в съёмку: `canvas.width === round(cssW × min(dpr,2))` — все четыре
строки `oneToOne: true`. Факт понижения попадает в замер: `stats()` отдаёт `fpsScale`,
`fpsAtDegrade`, `budgetScale`, `budgetCuts`, `degradations`; на всех четырёх кадрах
`fpsScale = 1` — то есть понижения не было, сцена рисовалась в полном разрешении, и это
видно в `live.json`, а не только на словах.

**Тесты.** `tests/bg3d.test.ts`:
- `разрешение: канвас 1:1 …` — 1425×767 при dpr 1 и 2850×1534 при dpr 2, `fpsScale = 1`,
  `budgetScale = 1`;
- `понижение разрешения — только по факту …` — в статистике есть все поля деградации;
- два старых теста переписаны осознанно: `ворота: средний Android …` ждал `renderScale 0,75`
  и `dprCap 1,5`, `4K-экран режет площадь кадра` ждал `renderScale < 1`. Оба требования
  отменены заданием, поэтому тесты проверяют **новое** поведение (1:1), а не старое.

## 2. Дефект 2: мобильная композиция 390×844

**Что было.** Хост 375×565, текст занимает y 26…533 почти по всей ширине. Машина
(квад 259×94) стояла на y **215…309** — ровно под лид-абзацем и кнопками.

**Что сделано (вёрстка не тронута).** На кадрах уже 0,80 (0,664 у 390×844, 0,88 у 768×1024)
посадка считается ОТ НИЗА кадра вверх, а не «где получилось, потом поднимем»:

`src/client/bg3d/plate.ts`
```ts
export const MOBILE_ASPECT = 0.80;
export const MOBILE_BOTTOM = -1.0;          // низ квада на нижней кромке кадра
if (aspect < MOBILE_ASPECT) {
  const hx = PLATE_HALF_LEN * scA;
  cy = MOBILE_BOTTOM + hx / PLATE_ASPECT;   // центр = низ + полувысота
}
```
Та же формула продублирована в `shader.ts` (`cp.y = -1.0 + PLATE_HALF*sc/PLATE_ASP`) и
читается CPU-портом `tools/bg3d/ref.mjs` через `platePlacement` — одна арифметика на
троих, как и требует шапка `plate.ts`.

Итог: квад 259×94 @87,**471** — машина целиком в последней полосе, свободной от текста;
линия земли (0,981 высоты файла) приходится на y 563, то есть шины стоят на кромке кадра.

**Доля видимых пикселей — числом.** Метод: кадр с текстом и кадр с погашенным текстом,
маска текста = разница двух кадров (порог 20/765), маска кузова = альфа `car-800.webp`
(≥ 128), «передняя часть» = правая треть файла (капот + линия ДХО). Время сцены на время
съёмки заморожено (`performance.now` → константа): без этого кадр успевал сдвинуться
между снимками, и число видимой доли прыгало 62 % → 81 % на одном и том же коде. После
заморозки три прогона подряд дают одно и то же значение.

| кадр | квад | видно кузова | видно передней части |
|---|---|---|---|
| 390×844 **до** | 259×94 @87,215 | 81,1 % | 96,4 % |
| **390×844 после** | 259×94 @87,471 | **94,9 %** | **97,7 %** |
| 390×844 dpr2 после | 519×187 @174,943 | 95,9 % | 97,8 % |
| 1440×900 (контроль, не сломан) | 413×149 @598,330 | 90,5 % | 100 % |

Про «до»: по маске кадра разница скромнее, чем по «на глаз» — силуэт стоял под текстом, но
из-под лида и кнопок выглядывали крыша и колёса, поэтому доля 81 %, а не 26 %. Существенно
другое: машина стояла МЕЖДУ строками текста, и её читали как артефакт за буквами. После
правки она стоит в свободной полосе целиком (см. `compare-390.jpg`: слева силуэт за
лид-абзацем, справа — в нижней полосе, над кромкой кадра).

Кадры: `before-390.jpg`, `after-390.jpg`, `after-390-notitle.jpg` (кадр без текста —
требование приёмки), `compare-390.jpg` (до/после рядом), `after-390-dpr2.jpg`,
`compare-1440.jpg`, полные экраны `*-screen.jpg` (PNG-исходники после расчёта удаляются:
`KEEP_PNG=1` оставляет их).

Честное ограничение: `after-390-*.jpg` сняты по клипу хоста (375×565) — это первый экран
без шапки; полный вьюпорт 390×844 — в `after-390-screen.jpg`. Скриншот отдаётся в

## 3. Гейт швов и альфа пластины (`scripts/bg3d-measure.mjs`, раздел 1b)

обе считаются каждый прогон `bg3d-measure`:

**Шов.** Длиннейший шов кадра — подряд идущая цепочка пикселей, где перепад к соседней
строке (или столбцу) ≥ 2,5 L. Порог: ни одного шва ≥ 200 px.

| 1440 dpr1 | 1425×767 | 0 px | ok |
| 1440 dpr2 | 2850×1534 | 0 px | ok |
| 390 dpr1 | 375×565 | 0 px | ok |
| 390 dpr2 | 750×1130 | 0 px | ok |

Самопроверка детектора (иначе «ни одного шва» значит только «детектор ничего не умеет»):

| мутант | результат |
|---|---|
| блок-подложка 300×120 поверх сцены (тот самый прямоугольник A12) | **поймана**, 340 px |
| крупное мягкое поле 8 L, период 180 px (свет, а не шов) | пропущена, 107 px — правильно |

Первая версия метрики считала внутристрочные перепады, а не линии, и не ловила даже

**Альфа пластины** — по самому файлу:

Требование «промежуточная альфа ≥ 10 % кромки» выполнено с запасом; углы прозрачны, то

### Две шкалы тона — почему обе

Числа приёмки круга 35 («кузов 28,0 L, σ 23,2, пол 16,8, контраст 11,2 L, средняя кадра
24,50») в отчёте r35 не записаны, поэтому здесь они воспроизведены заново двумя путями.

**1. CPU-порт** (`scripts/bg3d-tone.mjs`) — та же математика, что в шейдере, без
браузерного градиента, на **новом** разрешении:

| кадр | кузов | σ | дверь | пол | контраст | контраст по двери | средняя кадра |
|---|---|---|---|---|---|---|---|
| 1425×767 dpr1 | 77,3 L | 56,0 | 44,2 L | 9,4 L | 67,9 L | **34,8 L** | 12,91 |
| 2850×1534 dpr2 | 76,4 L | 58,3 | 43,5 L | 8,8 L | 67,6 L | **34,7 L** | 12,90 |
| 375×565 dpr1 | 74,4 L | 50,0 | 42,5 L | 6,0 L | 68,4 L | **36,5 L** | 16,74 |
| 750×1130 dpr2 | 74,0 L | 52,2 | 42,3 L | 6,0 L | 68,1 L | **36,3 L** | 16,74 |

Пороги контраста (8,1) и σ (12) выполняются на всех четырёх с запасом в 1,5–4×.

**2. Скриншот живой страницы** (`scripts/bg3d-live-shot.mjs`) — то, что видит посетитель,
уже под градиентом `.v-hero::after`: кузов 23,5…26,1 L, пол 9,8…10,7 L, контраст
13,2…16,0 L, σ 15,5…17,9 L; средняя первого экрана 1440×900 — **24,21 L**, на 390 —
**33,3 L**.

**Мобильный кадр: порог 8,1 L на 390 недостижим при текущем наложении страницы.**
Это измерено, а не предположено. На 390 силуэт после сдвига стоит в нижней полосе героя,
где тёмный скрим `.v-hero::after` непрозрачен на **93,3 %** (вертикаль .92 → .86 плюс
горизонталь .94 → .50, перемноженные как два слоя). Эффективные альфа и цвет скрима
восстановлены из двух наблюдаемых пар «сцена → кадр» (кузов 74,4 → 16,0 L, пол 6,0 → 10,7 L):
альфа 0,933, цвет ≈ 29,5 srgb. Отсюда потолок контраста в кадре при ЛЮБОЙ сцене
(кузов белый 255, пол чёрный 0) — **8,22 L**, то есть порог 8,1 L лежит на 99 % потолка.

| альфа наложения | потолок контраста кузов/пол |
|---|---|
| 0,933 (сейчас) | **8,2 L** |
| 0,86 | 10,9 L |
| 0,80 | 15,4 L |
| 0,70 | 22,6 L |

Порог 8,1 L достигается только при альфе наложения ≤ **0,897**. Порог σ ≥ 12 L при альфе
0,933 недостижим вовсе: он требовал бы внутреннего разброса кузова 179 L при шкале 0…100.

Факт после правки: кузов 16,0 L, пол 10,7 L, контраст **5,4 L** (66 % потолка), σ 7,2 L.
Проверено, что это не следствие посадки: подъём квада на 0,14 единицы (низ 471 → 432)
контраст не улучшил (3,1 L, пол поднялся до 12,9 L), потому что скрим там ещё плотнее у
края. Значит, дело в наложении CSS, а не в позиции машины.

Почему «до» показывал 13,2 L / 15,5 L: силуэт стоял МЕЖДУ строками текста, и замер
контраста считал соседом кузова тёмные глифы (3,1…4,5 L), а не пол. Это была не лучшая
картинка, а ошибка измерения на плохой композиции: контраст с текстом ничего не говорит о
том, видна ли машина. Поэтому «упавшие» числа — плата за правильную метрику, а не регресс.

Чтобы поднять контраст на 390 до порога, нужно ослабить скрим в нижней полосе героя до
альфы ≤ 0,897 — но это правка вёрстки (`.v-hero::after`), которую задание запрещает.
Масштаб внутри канваса этого не решает: скрим гасит и машину, и пол одинаково.

**Про среднюю кадра 24,3 и 24,21.** Цифра «24,50» из круга 35 — средняя кадра
`with-bg-1440.jpg`, снятого при **старом** разрешении: там канвас 855×460 растягивался на
1425×767, то есть в кадре был апскейл. Заново измеренная тем же кодом средняя того же
r35-кадра — **24,26 L**, пересъёмка текущего — **24,21 L**. Метод совпадает, разница в
содержимом сцены. Требование «средняя кадра ≥ 24,3 L **на новом разрешении**»
недотянуто на **0,08 L (0,3 %)**: при 1:1 сцена стала резче, но не темнее — средняя
определяется тёмным фоном, а не разрешением. Подгонять яркость фона ради +0,08 L я не
стал: это изменило бы палитру, которую задание запрещает трогать. Замер и расхождение —
в `live.json` (`screenMeanL`) и `tone.json`.
